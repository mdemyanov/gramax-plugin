## Находка: vacuous truth в буквальной формуле AC-002 (xargs на пустом вводе)

Буквальная формула AC-002 из текста требования:

```bash
grep -rlE 'code:' plugins/gramax/skills/writer/ \
  | xargs grep -liE 'cross-каталож' \
  | xargs grep -lE '`[A-Za-z0-9_-]+/[^`]+`' >/dev/null && echo PASS
```

Диспозиция предупреждает лишь об одном edge case этой формулы: «`code:`, «cross-каталож» и
паттерн `` `A/b` `` должны совпасть в одном файле — разнесение примера по двум файлам ломает
цепочку». Проверка эмпирически (macOS, `/usr/bin/xargs`, BSD-семантика — `xargs` не запускает
команду при пустом stdin и завершается кодом 0, не ошибкой) показала, что находка диспозиции —
только часть проблемы, и не в ту сторону, в которую предполагает слово «ломает»:

- **Прогон буквальной формулы на сегодняшнем репозитории** (0 файлов `skills/writer/`
  содержат `code:` вовсе — DEV-004 не начат) даёт `PASS`, не `FAIL`. Каждая стадия конвейера
  с пустым вводом не запускает `grep`, `xargs` завершается кодом 0, а `>/dev/null && echo PASS`
  проверяет только код возврата ПОСЛЕДНЕЙ стадии — не факт, что реальные данные прошли через
  всю цепочку.
- **Прогон на синтетической дизъюнктной фикстуре** (`code:` в файле A, `cross-каталож` в
  файле B — ровно тот сценарий, который диспозиция называет «ломает цепочку») тоже даёт
  `PASS`, не `FAIL` — по той же причине: вторая стадия получает пустой ввод (A не содержит
  `cross-каталож`), `xargs` третьей стадии тоже получает пустой ввод, снова код 0.

То есть буквальная формула АС-002 — не «строгий тест, который надо чуть доработать под edge
case диспозиции», а тест, вакуумно проходящий уже сегодня, до всякой реализации — тот же класс
дефекта, что описан в `content/lessons-learned.md` (запись 2026-08-11 «вакуумная истина в
негативных ассертах»), только здесь источник vacuous truth — не голое отрицание, а
положительная `&&`-идиома поверх `xargs`, чувствительная к пустому вводу на любой стадии.

**Исправление** (`tests/gramax/writer-consumer-rules/ac-002-cross-catalog-code-workflow-example.sh`):
явный цикл по кандидатам (файлы, содержащие `code:`) без `xargs`; если кандидатов 0 — явный
`FAIL` по позитивному предусловию, не молчаливый провал в пустоту; если кандидаты есть, для
каждого проверяется совпадение ОБОИХ оставшихся сигналов (`cross-каталож` и паттерн `` `A/b` ``)
в ТОМ ЖЕ файле. Проверено на 3 сценариях (см. README.md suite'а: 0 кандидатов → FAIL; все три
сигнала в одном файле → PASS; сигналы в разных файлах → FAIL).

**Урок для команды:** зафиксирован в `content/lessons-learned.md` — общий паттерн
`grep | xargs grep | xargs grep` с завершающим `>/dev/null && echo PASS` уязвим к vacuous truth
на платформах, где `xargs` по умолчанию не запускает команду при пустом stdin (macOS/BSD
подтверждено эмпирически).

## AC-011: решение PM — диспозиция принята как разрешающий документ, гейт зелёный

Первая версия этого at-design'а фиксировала AC-011 как открытый координационный вопрос:
буквальное требование называло ADR, диспозиция сама объявляла себя «design-документом, не
ADR» (`2026-08-11-writer-rules-disposition.md:20`), а «свободный следующий номер ADR-0014» из
диспозиции успел занять несвязанное решение (`0014-dual-publication-targets.md`, смержено
раньше в тот же день).

**PM решил вопрос явной правкой требования** (`content/30-requirements/
2026-08-11-writer-consumer-rules.md`, AC-011, правка датирована 2026-08-11): FR-076 называет
ADR ожидаемой, но не единственной формой разрешающего документа — («ожидаемо — ADR» в скобках
как ожидание, не мандат). Фактическим разрешающим документом принята диспозиция (Accepted),
которая сама обосновывает, почему она не ADR: enforcement и машиночитаемый контракт
закреплены параллельным ADR-0012, здесь только триаж. Новый критерий AC-011: разрешающий
документ существует, ссылается на требование по имени файла и несёт триаж всех шести тем A–F;
проверка идёт по наличию ссылки и полноте триажа, не по каталогу размещения
(`content/00-project/adr/` либо `content/40-architecture/`).

`ac-011-permitting-adr-references-requirement.sh` переписан под новый критерий — по прямому
указанию PM **строже** прежнего, не слабее: прежняя версия (буквальный грep из исходного
текста требования) была бы удовлетворена ЛЮБЫМ файлом в `adr/`, упоминающим имя требования, и
не проверяла полноту триажа. Новая версия — явный цикл по кандидатам в ОБОИХ каталогах: для
каждого кандидата, ссылающегося на требование, проверяется наличие ВСЕХ ШЕСТИ заголовков тем
(`^## A.` … `^## F.`) в ТОМ ЖЕ файле — отсутствие любой одной темы или разнесение ссылки и
триажа по разным файлам красит тест. Проверено на синтетических фикстурах: полный триаж в
одном файле → PASS; тот же файл без секции темы F → FAIL (см. README.md suite'а).

Тест зелёный сегодня, без ожидания DEV-004 — диспозиция уже удовлетворяет новому критерию.
Это третий regression guard suite'а (после AC-001, AC-012): он охраняет диспозицию от
будущей регрессии — если позже кто-то уберёт из неё ссылку на требование или одну из шести
секций триажа, гейт покраснеет.

## Boundary cases

- **AC-006 порядковая чувствительность.** `grep -A5` печатает совпавшую строку плюс 5 строк
  ПОСЛЕ неё; итоговый grep на 'статус'/'status' ищет только в этом окне. Если бы будущая
  реализация написала слово «статус» ДО упоминания «Тип контента ... ADR» (например, в
  предшествующем абзаце общего описания), тест не засчитал бы это — по замыслу диспозиции
  (edge case явно назван в брифе задачи QA-author). Формула сохранена буквально из требования,
  не переписана — проверено, что она ведёт себя ожидаемо и не даёт ложных срабатываний на
  сегодняшнем состоянии `doc-root-schema.md` (нет случайного совпадения «Тип контента»+ADR+
  статус где-то не по адресу).
- **AC-002 single-file constraint.** См. «Находка: vacuous truth» выше — граница
  операционализирована явным циклом с позитивным предусловием, не полагается на побочный
  эффект `xargs`.
- **AC-001/AC-012 как регрессия на физически смежные вставки.** Диспозиция размещает FR-066
  (backtick-ловушка) «рядом со строками 204–208» SKILL.md — та же секция «## Ссылки», где
  живёт правило, защищаемое AC-001; аккуратность этой вставки застрахована тем же тестом, что
  и исходное правило, а не отдельным AC. FR-072 (guardrail абсолютных путей) идёт в
  `## Guardrails` SKILL.md — не пересекается физически с AC-012 (references/drawio.md, другой
  файл); AC-012 остаётся значимым regression guard'ом сам по себе (защита синтаксиса drawio от
  ЛЮБОЙ из шести тем требования, даже если ни одна из них drawio не касается по смыслу).
- **AC-011 как третий regression guard, другого рода.** В отличие от AC-001/AC-012 (защищают
  фрагмент `plugins/gramax/skills/writer/**`, куда пойдёт DEV-004), AC-011 защищает документ
  ВНЕ периметра DEV-004 (`content/40-architecture/2026-08-11-writer-rules-disposition.md`) —
  граница ответственности за поддержание его зелёным другая: не Dev, а тот, кто в будущем
  правит диспозицию (SA/PM).
- **AC-004/AC-005 — не тестируют ВЫБОР решения, только его наличие.** По формулировке самих
  AC (BA-текст требования) допускается любой из трёх вариантов (а/б/в) для FR-067; диспозиция
  уже выбрала конкретный вариант («у потребителя») — тест на это не завязан умышленно, чтобы
  не дублировать архитектурное решение диспозиции внутри QA-artefact'а.

## Error cases

- **AC-002/AC-003/AC-008/AC-009 — позитивное предусловие перед негативной/составной
  проверкой.** Каждый из этих тестов сначала проверяет, что кандидаты (файлы с базовым
  сигналом) вообще существуют, и только потом — что среди них есть файл со ВСЕМИ требуемыми
  сигналами. Без этого шага пустой список кандидатов дал бы либо вакуумный `PASS` (см. находку
  AC-002), либо неинформативный `FAIL` без указания на то, что первопричина — полное
  отсутствие базового сигнала, не просто «сигналы разнесены».
- **AC-006 — файл не существует / не содержит секции вовсе.** Скрипт не различает «файла
  doc-root-schema.md не существует» (сегодня не так — файл есть) от «файл есть, но не
  содержит подраздела» — оба случая корректно дают `FAIL` через `grep -A5 ... 2>/dev/null`
  (подавление ошибки при отсутствующем файле не маскирует итоговый негативный результат
  второго grep'а).

## Не покрываем (вне scope)

- **Семантическая проверка примера FR-065 на живом двухкаталожном сетапе** (открытый вопрос
  BA №4 / диспозиция «Открытые вопросы» п.2). AC-002 проверяет только синтаксис одного файла
  (наличие `code:`, `cross-каталож`, паттерна `` `A/b` `` вместе) — не то, что построенная по
  этому рецепту ссылка реально резолвится в живом Gramax между двумя `.doc-root.yaml`-
  каталогами. Диспозиция сама называет единственный подтверждённый пример (репозиторий
  плагина, `code: GRAMAX-PLUGIN`) «без подтверждённого внешнего примера реально работающей
  ссылки» — проверка на реальном сетапе остаётся ручным шагом SA/QA, не автоматизируется этой
  задачей.
- **Выбор конкретного варианта (а)/(б)/(в) для FR-067/FR-068** — вне scope AC-004/AC-005 по
  замыслу самой BA-формулировки; тестируется факт наличия решения, не его содержание.
- **Выбор конкретного суб-варианта FR-069** (рекомендованный enum vs таблица соответствия)
  — AC-006 тестирует факт наличия рекомендации по `Статус` рядом с ADR, не то, какой из двух
  вариантов выбран; диспозиция сама выбрала гибридный подход (enum для новых каталогов +
  таблица для существующих с расхождением).
- **Создание отдельного ADR поверх диспозиции (FR-076)** — не требуется: PM принял диспозицию
  как разрешающий документ (см. «AC-011: решение PM» выше). Тест проверяет ФАКТ ссылки и
  полноту триажа в уже существующем документе, не форму документа.
