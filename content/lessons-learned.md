# Lessons Learned — gramax marketplace

> Append-only журнал. Каждая запись — короткий урок из реальной работы (фича, bug, surprise). Формат: `## YYYY-MM-DD — <тема>`, далее 3-5 строк: контекст / что узнали / как теперь делаем.

## 2026-05-08 — diagram-on-demand: симметрия mermaid/drawio в Research-фазе

**Контекст:** при декомпозиции фичи с двумя движками первый промпт Researcher'у был перекошен в сторону drawio (исходное предположение, что mermaid закрыт vendored claude-mermaid). Пользователь это заметил.

**Что узнали:** при разведке мультибэкендной фичи RES-промпт должен быть симметричным — равный объём подзадач и критериев сравнения на каждый бэкенд. Иначе вывод смещается.

**Как теперь делаем:** в `pm-agent`-промпте при декомпозиции фичи с N движками/бэкендами явно требовать симметричную RES-таблицу (Инструмент / Тип / Лицензия / Активность / AI-fit / Заметка) на каждый бэкенд + общий compare-блок.

## 2026-05-11 — sunset diagram-on-demand + diagrams skills

**Контекст:** major bump 1.4.0 → 2.0.0; удалили два собственных skill (`diagram-on-demand`, `diagrams`) и `scripts/drawio_convert.py`; drawio-функциональность делегирована внешнему плагину `Agents365-ai/drawio-skill`.

**Урок:** при sunset skill — обязательно проверять, что writer (или любой другой остающийся skill) не имеет hardcoded ссылок на удаляемые scripts. В нашем случае три места в writer-skill (SKILL.md + 2 references) требовали одновременного рефактора вместе с удалением. AC-016 «no orphan references» поймал это в TDD-фазе.

**Применимо:** любой будущий sunset публичного skill или скриптов в `plugins/gramax/`.

## 2026-05-12 — mermaid skill v4.0.0: переход на file-based workflow

**Что изменилось:** skill теперь создаёт `.mermaid`-файл через Write tool и вставляет тег-ссылку `<mermaid path="..."/>` вместо inline DSL.

**Почему:** формат Gramax всегда требовал file-based подход (задокументирован в blocks.md), но skill учил устаревшему inline-методу. Расхождение обнаружено при планировании PM.

**Что сработало:** обнаружение расхождения ground-truth (blocks.md) vs SKILL.md до начала работы Dev — позволило сформировать корректный spec сразу.

**ADR:** docs/adr/0010-mermaid-file-based-workflow.md

## 2026-05-08 — TDD-stubs могут быть частично зелёными от старта

**Контекст:** QA-author создал 12 stubs; 9 упали (требуют новых артефактов), 3 прошли сразу (тестируют уже существующие `drawio_convert.py`/`slugify.py`).

**Что узнали:** «failing stubs» — не догма. Если AC опирается на pre-existing функциональность, тест может быть зелёным сразу и это валидно: он защищает от регрессии. Главное — каждый stub отображается на номер AC и проверяет семантику, а не просто `[ -f x ]`.

**Как теперь делаем:** в `qa-author-agent`-промпте явно разрешать pre-passing stubs для AC, опирающихся на существующий код; помечать их в README тестов с пометкой «regression guard».

## 2026-08-09 — доставленный гейт впервые видит старый корпус

**Контекст:** миграция ADR, требований и отчётов в `content/` впервые подставила эти документы под `validate-content.py` (доставлен из nauta). Валидатор выдал 31 ошибку на примерах синтаксиса внутри код-блоков — ложные срабатывания, не дефекты документов.

**Что узнали:** гейт, доставленный извне, откалиброван на корпус, который писался вместе с ним. Переезд документов под такой гейт — это первая встреча валидатора с чужим корпусом, и первый прогон меряет не качество документов, а совпадение допущений.

**Как теперь делаем:** дефект в доставленном валидаторе чиним апстримом, не локальным патчем. Заведено как `tools-ai/nauta#1`, исправлено в v0.2.2. Первый прогон нового гейта на старом корпусе планируем как отдельный шаг с ожиданием ложных срабатываний.

## 2026-08-09 — план как артефакт для ревью

**Контекст:** самые дорогие находки цикла пришли не из работы исполнителей, а из чтения текста плана: узко очерченный периметр задачи, `WARN` там, где нужен `FAIL`, необъявленное требование `_index.md` для нового подраздела.

**Что узнали:** ошибка в плане тиражируется на всех исполнителей и обнаруживается только на приёмке. Субагент выполняет задачу так, как она сформулирована, и не оспаривает границы, которые ему назначили.

**Как теперь делаем:** план ревьюим до запуска исполнителей — тем же вниманием, что и код. Отдельно проверяем: периметр каждой задачи, уровень строгости проверок (WARN vs FAIL), полноту требований к новым артефактам.

## 2026-08-09 — `head` в конвейере, из которого пишется файл

**Контекст:** замер объёма работы делался как `grep … | tee файл | head -N`. `head` завершается после N строк, `tee` получает SIGPIPE и умирает — файл обрезается. Замер вышел втрое меньше реального.

**Как теперь делаем:** не ставить `head` в конвейер, из которого пишется файл. Сначала `grep … > файл`, отдельной командой `head файл`. Для замеров объёма — `wc -l` по записанному файлу, а не по хвосту конвейера.

## 2026-08-09 — фильтр заголовков дифа слепнет на markdown-буллетах

**Контекст:** для отсева заголовков дифа использовался `grep -vE '^[+-][+-]'`. На markdown-буллете `-- Spec: …` маркер дифа (`-`) плюс дефис буллета (`-`) дают `--` — строка отсеивалась как заголовок и выпадала из анализа.

**Как теперь делаем:** фильтровать заголовки дифа только точным паттерном `grep -vE '^(--- |\+\+\+ )'` — с пробелом и без класса символов. Общий урок: фильтр по «двум символам подряд» на текстовом корпусе почти всегда ловит лишнее.
