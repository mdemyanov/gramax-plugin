# Lessons Learned — gramax marketplace

> Append-only журнал. Каждая запись — короткий урок из реальной работы (фича, bug, surprise). Формат: `## YYYY-MM-DD — <тема>`, далее 3-5 строк: контекст / что узнали / как теперь делаем.

## 2026-05-08 — diagram-on-demand: симметрия mermaid/drawio в Research-фазе

**Контекст:** при декомпозиции фичи с двумя движками первый промпт Researcher'у был перекошен в сторону drawio (исходное предположение, что mermaid закрыт vendored claude-mermaid). Пользователь это заметил.

**Что узнали:** при разведке мультибэкендной фичи RES-промпт должен быть симметричным — равный объём подзадач и критериев сравнения на каждый бэкенд. Иначе вывод смещается.

**Как теперь делаем:** в `pm-agent`-промпте при декомпозиции фичи с N движками/бэкендами явно требовать симметричную RES-таблицу (Инструмент / Тип / Лицензия / Активность / AI-fit / Заметка) на каждый бэкенд + общий compare-блок.

## 2026-05-11 — sunset diagram-on-demand + diagrams skills

**Контекст:** major bump 1.4.0 → 2.0.0; удалили два собственных skill (`diagram-on-demand`, `diagrams`) и `scripts/drawio_convert.py`; drawio-функциональность делегирована внешнему плагину `Agents365-ai/drawio-skill`.

**Урок:** при sunset skill — обязательно проверять, что writer (или любой другой остающийся skill) не имеет hardcoded ссылок на удаляемые scripts. В нашем случае три места в writer-skill (SKILL.md + 2 references) требовали одновременного рефактора вместе с удалением. AC-016 «no orphan references» поймал это в TDD-фазе.

**Применимо:** любой будущий sunset публичного skill или скриптов в `plugins/gramax/`.

## 2026-05-12 — mermaid skill v4.0.0: переход на file-based workflow

**Что изменилось:** skill теперь создаёт `.mermaid`-файл через Write tool и вставляет тег-ссылку `<mermaid path="..."/>` вместо inline DSL.

**Почему:** формат Gramax всегда требовал file-based подход (задокументирован в blocks.md), но skill учил устаревшему inline-методу. Расхождение обнаружено при планировании PM.

**Что сработало:** обнаружение расхождения ground-truth (blocks.md) vs SKILL.md до начала работы Dev — позволило сформировать корректный spec сразу.

**ADR:** content/00-project/adr/0010-mermaid-file-based-workflow.md

## 2026-05-08 — TDD-stubs могут быть частично зелёными от старта

**Контекст:** QA-author создал 12 stubs; 9 упали (требуют новых артефактов), 3 прошли сразу (тестируют уже существующие `drawio_convert.py`/`slugify.py`).

**Что узнали:** «failing stubs» — не догма. Если AC опирается на pre-existing функциональность, тест может быть зелёным сразу и это валидно: он защищает от регрессии. Главное — каждый stub отображается на номер AC и проверяет семантику, а не просто `[ -f x ]`.

**Как теперь делаем:** в `qa-author-agent`-промпте явно разрешать pre-passing stubs для AC, опирающихся на существующий код; помечать их в README тестов с пометкой «regression guard».

## 2026-08-09 — доставленный гейт впервые видит старый корпус

**Контекст:** миграция ADR, требований и отчётов в `content/` впервые подставила эти документы под `validate-content.py` (доставлен из nauta). Валидатор выдал 31 ошибку на примерах синтаксиса внутри код-блоков — ложные срабатывания, не дефекты документов.

**Что узнали:** гейт, доставленный извне, откалиброван на корпус, который писался вместе с ним. Переезд документов под такой гейт — это первая встреча валидатора с чужим корпусом, и первый прогон меряет не качество документов, а совпадение допущений.

**Как теперь делаем:** дефект в доставленном валидаторе чиним апстримом, не локальным патчем. Заведено как `tools-ai/nauta#1`, исправлено в v0.2.2. Первый прогон нового гейта на старом корпусе планируем как отдельный шаг с ожиданием ложных срабатываний.

## 2026-08-09 — план как артефакт для ревью

**Контекст:** самые дорогие находки цикла пришли не из работы исполнителей, а из чтения текста плана: узко очерченный периметр задачи, `WARN` там, где нужен `FAIL`, необъявленное требование `_index.md` для нового подраздела.

**Что узнали:** ошибка в плане тиражируется на всех исполнителей и обнаруживается только на приёмке. Субагент выполняет задачу так, как она сформулирована, и не оспаривает границы, которые ему назначили.

**Как теперь делаем:** план ревьюим до запуска исполнителей — тем же вниманием, что и код. Отдельно проверяем: периметр каждой задачи, уровень строгости проверок (WARN vs FAIL), полноту требований к новым артефактам.

## 2026-08-09 — `head` в конвейере, из которого пишется файл

**Контекст:** замер объёма работы делался как `grep … | tee файл | head -N`. `head` завершается после N строк, `tee` получает SIGPIPE и умирает — файл обрезается. Замер вышел втрое меньше реального.

**Как теперь делаем:** не ставить `head` в конвейер, из которого пишется файл. Сначала `grep … > файл`, отдельной командой `head файл`. Для замеров объёма — `wc -l` по записанному файлу, а не по хвосту конвейера.

## 2026-08-09 — фильтр заголовков дифа слепнет на markdown-буллетах

**Контекст:** для отсева заголовков дифа использовался `grep -vE '^[+-][+-]'`. На markdown-буллете `-- Spec: …` маркер дифа (`-`) плюс дефис буллета (`-`) дают `--` — строка отсеивалась как заголовок и выпадала из анализа.

**Как теперь делаем:** фильтровать заголовки дифа только точным паттерном `grep -vE '^(--- |\+\+\+ )'` — с пробелом и без класса символов. Общий урок: фильтр по «двум символам подряд» на текстовом корпусе почти всегда ловит лишнее.

## 2026-08-09 — `"$VAR:text"` без фигурных скобок молча портит значение в zsh

**Контекст:** сверка архива `tests/gramax/archive/` с базовым коммитом строилась на
`git show "$BASE:tests/gramax/$s/$rel"`. Bash-тул харнесса фактически исполняет команды через
zsh (не через `sh`/`bash`, несмотря на имя тула). В zsh голая подстановка `$VAR:буква…` вне
фигурных скобок разбирается как history-подобный модификатор параметра (`:t` tail/basename,
`:h` head/dirname, `:a` абсолютный путь, `:r` без расширения) — **даже внутри двойных кавычек**,
без всякого `!`. `$BASE:tests/…` съело `:t` из «tests», аргумент `git show` превратился в
нечитаемую строку без разделителя `revision:path`, `git show` упал на каждом файле, и все 62
файла архива ошибочно показали `DIFF:` — притом что `git mv` ничего не менял (независимая
проверка `git diff --cached -M100%` подтвердила 62/62 `rename (100%)`).

**Как теперь делаем:** переменную, за которой в той же строке следует `:`, всегда оборачивать в
`${VAR}` (`"${BASE}:tests/…"`), а не полагаться на голое `$VAR:`. Правило шире git-revision:path —
любая конструкция `"$X:суффикс"` в командах через этот харнесс подозрительна и требует фигурных
скобок. При «повальном» `DIFF`/mismatch на 100% элементов выборки — сначала проверить, не
исказился ли сам аргумент сравнения, прежде чем подозревать данные.

## 2026-08-10 — «зелёный по грепу» — не зелёный

**Контекст:** `bash scripts/check.sh --full` был красным весь цикл — шаг `shellcheck` падал на
94 замечаниях, из которых 62 были ложным `SC1091` из-за способа вызова, а 70 лежали в
замороженном `tests/gramax/archive/**`. Постановка задачи цикла при этом утверждала, что оба
suite (`orphan-references`, `nauta-integration`), подключённые к `--full`, зелёные, и это было
верно — но координатор докладывал «`--full` зелёный» про весь агрегатор целиком, хотя ни разу не
проверял его составной код возврата: вывод читался через `grep`/`tail`, которые отфильтровывали
или обрезали строку `FAIL: shellcheck issues` и итоговый `RESULT: FAIL`, оставляя на виду только
зелёные строки suite'ов. Расхождение вскрылось лишь на финальном ревью прогоном на стартовом
коммите цикла (`c9be893`) — гейт был красным ещё **до** начала работ.

**Что узнали:** составной гейт (`check.sh`, `run.sh` агрегатора) нельзя признавать зелёным по
наличию ожидаемых строк в отфильтрованном выводе — только по коду возврата всего вызова
(`bash scripts/check.sh --full; echo "exit=$?"` → обязан быть `0`) или по строке `RESULT:` без
предварительной фильтрации. `grep`/`tail`/`head` в конвейере, через который читается вердикт
составного гейта, систематически создают иллюзию «зелёного», отфильтровывая именно ту строку,
которая несёт отрицательный результат.

**Как теперь делаем:** вердикт составного гейта — только по `$?` после полного прогона без
фильтрации вывода, или по факту, что `RESULT: PASS`/`RESULT: FAIL` — последняя строка
непрефильтрованного лога. Перекликается с уроком про `head` в конвейере, из которого пишется
файл (см. выше 2026-08-09) — тот про усечение данных при записи, этот про усечение вердикта при
чтении; оба — частный случай одной ошибки: неполный конвейер перед выводом, которому доверяют.

## 2026-08-11 — красный TDD-stub, который нельзя погасить корректной работой, хуже отсутствующего

**Контекст:** QA-author (`tests/gramax/catalog-validator/ac-011…`, AC-005 требования
`2026-08-11-validation-contract.md`) написал тест, сравнивающий будущий JSON-контракт тегов на
**равенство** с константами `PAIRED_TAGS`/`SELF_CLOSING`, извлечёнными регуляркой из живого
`validate_structure.py`. Второе PM-ревью нашло: ADR (`0012-catalog-validation-contract.md`
Решение 3) прямо предписывает будущему DEV-001 **удалить** эти литералы — код должен читать JSON
вместо хардкода. Тест сравнивал с тем, что задача сама же требует стереть — не мог позеленеть НИ
ПРИ КАКОЙ корректной реализации.

**Что узнали:** красный TDD-stub, у которого нет пути к зелёному через правильную работу
Dev'а, — не «строгий тест», а испорченный тест: он тихо меняет стимул с «сделай правильно» на
«сделай так, чтобы я замолчал», и Dev с высокой вероятностью выберет более дешёвый путь
(оставить хардкод) — тест начинает защищать то самое нарушение архитектуры (здесь — BR-002,
«не больше одного источника правды»), которое должен был ловить. Отдельно нашлась вторая ловушка
того же теста: равенство с СЕГОДНЯШНИМ (заведомо неполным — без тега `drawio`) состоянием
константы дало бы ложный провал и на корректном, полном будущем контракте.

**Как теперь делаем:** для каждого stub, сравнивающего артефакт с деталью текущей реализации
(константа, литерал, конкретный путь в коде), задаём явный вопрос до коммита: «переживёт ли
эта деталь ту работу, которую ADR предписывает сделать правильно?» Если ADR предписывает деталь
убрать — сравнение с ней делаем условным (при отсутствии детали — `N/A`, не провал), а
неизменную часть требования (здесь — FR-038 «контракт содержит как минимум») фиксируем
литерально в самом тесте, не выводим из кода, который тест же и заставляет меняться.

## 2026-08-11 — два зеркальных варианта того же дефекта: тест не может стать красным по правильной причине

**Контекст:** QA-author (`tests/gramax/mermaid-adoption/`, требование
`2026-08-11-mermaid-file-based-adoption.md`) писал stub'ы для функциональности, которой ещё
нет вообще (DEV-003 не начат). Нашлись два разных способа, которыми красный stub оказывается
красным не по содержательной причине — оба обнаружены до коммита прогоном на текущем
состоянии репозитория, не постфактум.

**Вариант A — буквальный текст AC уже удовлетворён случайно.** AC-001 требования содержит
готовую BA-формулировку ассерта: `grep -rliE '\.doc-root\.yaml' plugins/gramax/skills/mermaid/
plugins/gramax/README.md`. Прогон на текущем репозитории показал: assert **уже проходит**,
хотя граница юрисдикции (FR-050/FR-051), которую он должен подтверждать, нигде не
задокументирована — `SKILL.md` упоминает `.doc-root.yaml` по совершенно другой причине
(определение XML/Markdown-синтаксиса каталога). Тот же паттерн повторился на AC-009: голая
проверка «`blocks.md` упоминается где-то в `skills/mermaid/`» тоже была бы pre-passing —
`SKILL.md` уже цитирует `blocks.md` как источник дефолтов `width`/`height`, не как контракт
рендера для конфликта валидатора.

**Вариант B — вакуумная истина в негативных ассертах.** AC-003/AC-006/AC-007 формулируются
как отсутствие эффекта («файл не в отчёте», «фикстура не изменилась», «повтор ничего не
меняет»). Пока инструмента не существует, он не запускается вообще — отсутствие эффекта
тривиально истинно без всякой заслуги реализации; голый негативный ассерт был бы зелёным без
единой строчки кода Dev.

**Что узнали:** оба варианта — противоположные проявления одного дефекта: assert проходит
(или не может не пройти) по причине, не связанной с содержанием AC, а не потому что
требование выполнено. Это зеркало урока 2026-08-11 выше («красный stub, который нельзя
погасить корректной работой») — там assert не мог стать зелёным никогда, здесь он не может
быть красным по правильной причине. Обе версии одинаково обесценивают TDD-сигнал: заставляют
Dev либо чинить то, что не сломано, либо не показывают, что действительно нужно починить.

**Как теперь делаем:** для буквальных AC-формулировок — прогонять ассерт на текущем
репозитории ДО коммита stub'а; если проходит незаслуженно, добавлять семантическое усиление
(ключевое слово по существу AC, не просто более узкий grep) и держать буквальную формулировку
только как трассируемость с BA, не единственный барьер. Для негативных/сравнительных
ассертов (diff, отсутствие в выводе, «не изменилось») — всегда предварять их позитивной
гарантией, что проверяемый механизм реально сработал (нашёл, создал, изменил) — иначе
«ничего не произошло» и «работает корректно» неотличимы для теста.

## 2026-08-11 — реализацию подогнали под фикстуру вместо фикстуры под реализацию

**Контекст:** `check_orphans` (FR-047, ADR-0012 Решение 2 — «эквивалент проверки C10»)
первой версией сузили: проверка пропускала файл, если он был единственной содержательной
статьёй в своей директории — иначе краснели два уже зелёных теста
(`GoodCatalogTests`/`RootIndexTests`), чьи минимальные фикстуры держали ровно один
несвязанный файл на директорию. Эталон C10 (`scripts/validate-content.py::check_orphans`)
такого исключения не делает: любая `.md`, кроме `_index.md`, с нулевой входящей степенью —
сирота, без условий по числу соседей.

**Что узнали:** когда деталь реализации введена специально, чтобы не покраснел
существующий тест на минимальной фикстуре — это тот же класс ошибки, что «неубиваемый
тест» выше (2026-08-11), только с обратной стороны: там тест подгоняли под код, который
ADR предписывал убрать; здесь код подгоняли под фикстуру, которая просто не была связной.
Само по себе прохождение теста не подтверждает, что реализация соответствует контракту
(здесь — ADR со ссылкой на конкретный эталон C10) — если тест начинает диктовать сужение
контракта, которое нигде не описано и не согласовано, надо чинить фикстуру (сделать её
представительной), а не контракт.

**Как теперь делаем:** если реализация вводит исключение из формулировки ADR/AC, чтобы
удержать существующий тест зелёным, — это красный флаг сам по себе, требующий явной
проверки «есть ли для этого исключения основание в ADR, а не только в форме конкретной
фикстуры». Минимальные фикстуры (по одному файлу на директорию) для orphan-подобных
проверок непредставительны по конструкции — на них тривиально «зелено» просто по
отсутствию других кандидатов; такие фикстуры для проверок связности нужно делать связными
(взаимной перекрёстной ссылкой между файлами), а не полагаться на то, что нулевая
связность сама по себе не нарушение.

## 2026-08-11 — `grep | xargs grep | xargs grep` молча PASS'ит при пустом вводе на любой стадии

**Контекст:** QA-author (`tests/gramax/writer-consumer-rules/`, требование
`2026-08-11-writer-consumer-rules.md`, AC-002) готовился использовать буквальную BA-формулу
из текста AC как есть: `grep -rlE 'code:' … | xargs grep -liE 'X' | xargs grep -lE 'Y'
>/dev/null && echo PASS`. Диспозиция предупреждала только об одном edge case («разнесение
примера по двум файлам ломает цепочку»). Прогон на текущем репозитории (0 файлов содержат
`code:` вовсе — DEV-004 ещё не начат) показал: формула печатает `PASS`, а не `FAIL`. Причина —
`xargs` на этой платформе (macOS, `/usr/bin/xargs`, BSD-семантика) не запускает команду при
пустом stdin и завершается кодом 0; `>/dev/null && echo PASS` проверяет только код возврата
ПОСЛЕДНЕЙ стадии конвейера, не факт, что данные реально прошли через все стадии. Тот же эффект
воспроизведён и на синтетической фикстуре ровно того сценария, который диспозиция называла
«ломает цепочку» (сигналы в разных файлах) — снова тихий `PASS`, не `FAIL`.

**Что узнали:** идиома `grep | xargs grep | xargs grep …>/dev/null && echo PASS` — не «более
строгая цепочка условий», а тест, вакуумно проходящий ДО всякой реализации, если хотя бы одна
промежуточная стадия может получить пустой ввод (что почти всегда верно до того, как Dev
начал работу). Это тот же класс дефекта, что «вакуумная истина в негативных ассертах» (см.
запись выше, 2026-08-11) — только источник здесь не голое отрицание, а положительная
`&&`-идиома поверх `xargs`, чувствительная к пустому stdin на любой стадии.

**Как теперь делаем:** для многоступенчатой grep-цепочки, где промежуточный результат может
оказаться пустым до реализации фичи, — не полагаться на код возврата хвоста конвейера с
`xargs`. Вместо этого: явный цикл по кандидатам первой стадии (`while IFS= read -r f; do …
done < <(grep -rl … )`), явная проверка «кандидатов вообще ≥1» как отдельное позитивное
предусловие, и проверка остальных сигналов внутри цикла по каждому файлу отдельно. Перед
коммитом любой grep-цепочки с `xargs` — прогнать её на сегодняшнем (домашинном) состоянии
репозитория и явно проверить код возврата, а не полагаться на то, что «нет вывода» и «нет
ошибки» — разные вещи для `xargs`.

## 2026-08-11 — пример из SA-артефакта уехал в публикуемый материал плагина, не пройдя проверку на пригодность к публикации

**Контекст:** диспозиция `2026-08-11-writer-rules-disposition.md` (тема B/C, FR-067/FR-069)
предписывала Dev дословные примеры из research-разведки — «по образцу `knowlage/moex`»,
«пример: `mango-cti-rest`» — как иллюстрацию найденных на практике случаев (вложенный
`.doc-root.yaml`, разошедшийся enum статуса). Dev перенёс их буквально в
`plugins/gramax/skills/writer/references/doc-root-schema.md` — потребительский справочник,
который уезжает каждому, кто ставит плагин. Именование приватных сторонних репозиториев в ADR
и требованиях легитимно (фиксация факта разведки, уже опубликовано); в публикуемом материале
skill'а — нет. Ни Dev, ни QA (12/12 зелёных, оба гейта чистые) этого не заметили — поймал
только secrets sweep перед `git push`.

**Что узнали:** архитектурный документ может предписать исполнителю деталь, корректную по
месту происхождения (SA-артефакт, зафиксированный факт), но непригодную по месту назначения
(публикуемый материал с другим периметром распространения) — сам SA-артефакт эту границу не
проверяет, потому что она не входит в его зону ответственности (архитектурная корректность
примера, не его публикуемость). TDD-гейты (grep по сигналам темы) тоже не ловят это: ассерты
проверяют наличие содержательного сигнала («overlay», «вложенн.*doc-root», «источник истины»),
а не факт наличия чужого имени репозитория — pass по существу и нарушение по периметру
публикации оказались ортогональны друг другу.

**Как теперь делаем:** пример, который переносится из SA-артефакта (ADR, диспозиция,
требование) в публикуемый материал плагина (`SKILL.md`, `references/*.md`, `CHANGELOG.md`),
проверяется на пригодность к публикации отдельно от технической корректности переноса —
не «звучит ли предложение SA дословно», а «можно ли назвать источник примера, если материал
уедет наружу». Приватное имя репозитория/организации в таком примере заменяется на
обезличенное описание сути случая («сторонний каталог-потребитель со вложенным
`.doc-root.yaml`», «`# добавлено overlay'ем <имя-оверлея>`») без потери содержательной
ценности — образец такого обезличения уже есть в `plugins/gramax/skills/mermaid/references/
jurisdiction-and-validation.md` («класс конфликта», без называния конкретного репозитория).

## 2026-08-13 — PM запустил два BA параллельно, не разметив диапазоны идентификаторов

**Контекст:** волна по формам ссылок декомпозирована на две параллельные BA-задачи — контракт
формы ссылки ([2026-08-13-link-form-contract.md](30-requirements/2026-08-13-link-form-contract.md))
и ретракция кросс-каталожного рецепта
([2026-08-13-cross-catalog-retraction.md](30-requirements/2026-08-13-cross-catalog-retraction.md)).
Оба брифа велели продолжать сквозную нумерацию FR августовской волны, но ни один не назвал
диапазон. Обе задачи независимо стартовали с FR-077 и заняли FR-077…085. Поймано PM'ом грепом по
диапазону, пока вторая задача ещё работала; исправлено сообщением в живого субагента
(перенумерация в FR-093…103) до её завершения. Ирония: коллизия возникла в той самой волне,
которая вводит правило против неразрешимых отсылок `FR-NNN` — за отсутствие такого правила в
майских требованиях (`FR-001` определён в пяти разных документах) и взялись.

**Что узнали:** сквозная конвенция нумерации не защищает от коллизии при параллельном запуске —
она задаёт лишь **направление** («продолжай, не начинай с 001»), а не **точку старта**. Пока
задачи шли последовательно, точка старта выводилась из корпуса и была однозначной; параллельный
запуск ломает это допущение молча, потому что оба агента читают один и тот же корпус и приходят к
одному и тому же следующему свободному номеру. То же верно для любого монотонного идентификатора,
раздаваемого из общего пространства: ADR-NNNN, номера suite'ов, версии.

**Как теперь делаем:** PM, запуская две и более задачи, порождающие идентификаторы из общего
пространства, закрепляет диапазон за каждой **в брифе** («ADR-0016 закреплён за тобой; ADR-0017
занят параллельной задачей») — не «продолжай нумерацию». Тот же приём применяется к записи в общий
файл-реестр: при параллельном запуске строку в `_index.md` добавляет ровно один агент, остальным
это запрещено явно, а PM вносит недостающие строки сам — иначе два агента правят один файл
одновременно. Проверка после параллельной фазы — грепом по занятому диапазону во всех артефактах
волны, до передачи следующей роли.

## 2026-08-13 — копия регулярки валидатора для аудита обязана быть побайтовой, не «эквивалентной»

**Контекст:** для research-аудита форм ссылок (`2026-08-13-link-form-corpus-audit.md`) понадобилось
воспроизвести маскирование код-спанов, которое `_mask_code` делает в обоих живых валидаторах
(`scripts/validate-content.py`, `plugins/gramax/scripts/validate_structure.py`), чтобы найти именно
то, что C9/C10 не видят. Инструмент аудита переписал `_INLINE_CODE_RE` «по смыслу» —
`(`+)([^`\n]+?)\1` вместо оригинального `(`+)([^\n]+?)\1` (исключил бэктик из класса символов внутри
спана, показалось эквивалентным и даже «безопаснее»). На корпусе это тихо разошлось на строке,
которая специально написана как двойно-экранированный код-спан вокруг markdown-синтаксиса —
`` `` `[X](Y)` `` `` — и дало 3 ложных «битых markdown-ссылки» там, где ссылок вообще нет.
Ирония: этот же класс риска («чужой regex-валидатор не отличает код-спан от настоящей ссылки»)
уже описан в самом корпусе как FR-065/FR-066 (`2026-08-11-writer-consumer-rules.md:125`,
`2026-08-11-writer-rules-disposition.md:56`) — аудит наступил на грабли, которые сам же
исследовал.

**Что узнали:** при воспроизведении логики живого валидатора для стороннего инструмента (аудит,
линтер, отчёт) — «эквивалентная по смыслу» регулярка не эквивалентна; малейшее сужение класса
символов ломается именно на пограничных случаях (вложенные/разной длины бэктик-заборы), которые и
были причиной, по которой оригинальная регулярка написана так, а не иначе. Расхождение находится не
сразу — оно даёт не ошибку, а тихо неверный результат на конкретных строках.

**Как теперь делаем:** копируя маскирующую регулярку из `scripts/validate-content.py` или
`plugins/gramax/scripts/validate_structure.py` для стороннего инструмента — копировать её
дословно (включая класс символов), не «по смыслу», и после копирования прогонять новый инструмент
на корпусе, специально проверяя строки, где валидатор уже документирует пограничный случай (здесь —
FR-065/FR-066). Несовпадение результата с реальным прогоном самого валидатора (`Errors: 0 |
Warnings: 0`) — сигнал разошедшейся регулярки, а не находка нового дефекта корпуса.

## 2026-08-13 — расхождение двух валидаторов на одной и той же ссылке блокирует не только миграцию, но и будущее органическое письмо

**Контекст:** ADR-0016 чинил ложный error `check_broken_links` на markdown-ссылке без расширения
(`[X](doc)`, форма, которую уже сегодня предписывает `SKILL.md:210`). Фикс в
`plugins/gramax/scripts/validate_structure.py` — наш файл, дёшево. Но `scripts/validate-content.py`
(nauta), подключённый к `check.sh --fast` на каждый коммит, несёт тот же буквальный `.exists()`-
дефект и не в нашей юрисдикции. Первая мысль — «дефект касается только миграции 103 код-спанов»,
что занижало срочность.

**Что узнали:** правило `SKILL.md:210` действует уже сейчас, независимо от миграции — значит любая
НОВАЯ, органически написанная ссылка без расширения (не только результат миграции) сразу же красит
`check.sh --fast` через непочиненный чужой валидатор. Расхождение двух валидаторов на одном и том же
классе ссылок — это не отложенная проблема одной задачи, а активная растяжка под всем правилом,
которое плагин уже документирует потребителям. Оценивать срочность фикса стороннего валидатора по
объёму миграции, а не по тому, что правило уже действует, — заниженная оценка риска.

**Как теперь делаем:** при обнаружении, что офлайн-гейт снаружи нашей юрисдикции (nauta, любой
чужой скрипт) расходится с уже опубликованным правилом `SKILL.md`, проверять в первую очередь не
«сколько объектов нужно мигрировать», а «может ли кто-то ПРЯМО СЕЙЧАС, следуя уже опубликованному
правилу, покрасить `check.sh --fast»`. Если да — вводить явный временный протокол (не канонический,
но безопасный для обоих валидаторов синтаксис) немедленно, не дожидаясь исполнения миграции или
апстрим-фикса (см. ADR-0016 Решение 2, `content/00-project/adr/0016-link-form-contract.md`).
