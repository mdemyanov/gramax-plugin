# ADR-0020: Рекурсивное обнаружение `.doc-root.yaml` и типизация обязательных полей в `validate_structure.py`

**Status:** Accepted
**Date:** 2026-08-13
**Plugin:** gramax / marketplace

## Context

Инцидент 2026-08-13: редактор Gramax (`editor.nau.im`) не открывался у пользователей воркспейса. Причина — 24 файла `.doc-root.yaml` в 12 подключённых каталогах со строкой `title: {{PROJECT_NAME}} — KB команды` без кавычек. В YAML `{{` открывает flow mapping, поэтому `title` — не строка, а dict; JS-парсер Gramax в мягком режиме отдаёт объект и падает. Все 24 файла лежали **не** в корне каталога, а в скопированной из шаблона папке `examples/<профиль>-example/content/`.

Ключевой факт: **Gramax ищет catalog root, сканируя весь репозиторий**, а не только переданный путь. `validate_structure.py content` на тех же репозиториях давал exit 0. Три пробела относительно реального поведения Gramax (требование [Контракт .doc-root.yaml: рекурсивное обнаружение и типизация title](../../30-requirements/2026-08-13-doc-root-discovery-contract.md), FR-120…FR-123, AC-036…AC-040):

1. **Область обнаружения.** `validate()` (`validate_structure.py:447`) читает ровно `root/.doc-root.yaml` через `check_doc_root()` (`:70-83`). Вложенные `.doc-root.yaml` глубже по дереву не валидируются никогда. `check_orphans()` про них знает (`in_scope=False`) — но только чтобы **исключить**; Gramax же, наоборот, их включает.
2. **Типизация полей.** `check_doc_root()` проверяет лишь присутствие ключа (`field not in data`), не тип. `docRootRequiredFields = [title, language, syntax]` проходит при `title: 4.21` (float), `title: yes` (bool), `title: {a: b}` (dict) — ровно класс дефекта инцидента.
3. **Негашение диагностики.** При неудаче `check_doc_root()` (в т.ч. `invalid yaml`) `validate()` делает ранний `return` (`:447-448`) — остальная диагностика, включая `check_placeholders`, не выполняется; сообщение схлопывается до `invalid yaml: <str(e)>`. Незакавыченный `{{...}}`, при котором файл не парсится вообще, ни одной фикстурой не покрыт (слепое пятно `placeholder-leak`, покрывающего только закавыченный `{{TSN_CODE}}`).

Предшественники: ADR-0012 (контракт валидации: JSON single source of truth BR-002, perimeter Решение 6, прецедент suite/разрешения на marketplace.json), ADR-0019 (паттерн «одна находка на дефект» BR-004, демаркация ownership, образец структуры и тона), ADR-0006 (semver).

## Решение 1 — FR-120: рекурсивное обнаружение catalog root

**Решение:** `validate()` обходит всё дерево переданного пути и валидирует **каждый** найденный `.doc-root.yaml` как отдельный catalog root полным набором структурных проверок (типизированный `check_doc_root`, `_index.md`, frontmatter, теги, плейсхолдеры, ссылки, сироты, изображения, диаграммы, W034). Gramax-семантика «сканирую весь репозиторий» становится семантикой валидатора.

**Исключения обхода — явный список (FR-120):**
- по имени каталога на любой глубине: `.git`, `.gramax`, `node_modules`;
- по относительному пути от переданного корня: `tests/**` и `plugins/gramax/scripts/tests/fixtures/**` — фикстурные пути догфудинга (AC-040, Решение 6).
- Сам переданный корень исключению не подлежит: валидация primary-root выполняется всегда, даже если его имя совпадает с исключаемым (прогон на fixture-корне `orphan-cross-catalog-boundary` обязан находить вложенные `catalog-a`/`catalog-b`).

**Границы ownership (BR-004):** файл принадлежит ровно одному root — ближайшему предку с `.doc-root.yaml`. Поддеревья вложенных root исключаются из структурной области ancestor-каталогов (переиспользование границы `in_scope=False`, FR-047): статья вложенного каталога не считается сиротой внешнего, ссылки/изображения резолвятся в границах своего root (AC-039). Дефект даёт ровно одну находку: битый вложенный `.doc-root.yaml` — одно error-сообщение, не дубль от ancestor.

**Детерминизм:** обход отсортирован, находки внутри файла упорядочены по номеру строки (NFR-002, дух ADR-0019 Решение 8).

## Решение 2 — FR-121: типизация обязательных полей `.doc-root.yaml`

**Решение:** для каждого поля из `docRootRequiredFields` (`title`, `language`, `syntax`) проверяется не только присутствие, но и тип. Правило **едино для всех трёх полей**: значение обязано быть **непустой строкой**. `dict`/`list`/`bool`/`int`/`float`/`date`/`null`/пустая строка → `error` с фактическим типом значения и исходной строкой файла (номер строки + raw-текст). Отсутствие ключа — существующий `missing field: ...`.

**Почему едино для `language`/`syntax`, а не только `title`:** дефект одного класса (значение, которое Gramax не парсит как строку каталога-метаданных), исправление одно (закавычить), потребление одно. `language: yes` (bool) или `syntax: 42` (int) роняют редактор так же, как `title: {a: b}`; раздельная семантика потребовала бы двух правил без обоснования.

## Решение 3 — FR-122/FR-123: негашение диагностики и подсказка закавычивания

**Решение:** ранний `return` при неудаче `check_doc_root()` (`validate_structure.py:447-448`) **убирается для существующего файла с ошибкой парсинга**: `yaml.YAMLError` в одном `.doc-root.yaml` не прекращает прогон, все проверки выполняются для каждого найденного root. Минимум — `check_placeholders` обязателен даже для root с непарсящимся `.doc-root.yaml` (читает raw-текст, не AST — работает и на битом файле). Отсутствие `.doc-root.yaml` на переданном корне сохраняет прежнее поведение (error + прекращение): директория без catalog root не является каталогом, структурным проверкам не к чему привязаться.

**Сообщение об ошибке парсинга:** номер строки и колонки из исключения pyyaml (`problem_mark.line`/`.column`), а не `str(e)`; при отсутствии mark — fallback на `str(e)`.

**FR-123 подсказка:** если парсинг упал из-за незакавыченного `{{...}}` (эвристика по raw-строке: плейсхолдер на позиции значения поля), сообщение дополняется конкретным исправлением — `title: "{{PROJECT_NAME}}"` (кавычки), а не только констатацией ошибки.

**Одна находка на дефект (BR-004):** parse-error-находка с подсказкой FR-123 поглощает placeholder-находку того же токена (паттерн «киллер поглощает балансную», ADR-0019 Решение 3): `title: {{PROJECT_NAME}}` даёт ровно одно сообщение. Прочие `{{...}}`-токены того же файла (закавыченные или mid-scalar, где YAML парсится) продолжают давать собственные placeholder-находки через `check_placeholders`.

## Решение 4 — Q1: «лишний catalog root в служебной папке» — отдельный warning не вводится

**Решение:** отдельного уровня для «extra catalog root под `examples/`/`tests/fixtures/`» **не вводится**; фиксируются только фактические ошибки FR-120/FR-121.

**Почему:**
- Нет универсального критерия «служебной папки» (perimeter, ADR-0012 Решение 6): `examples/` у части потребителей — легитимная витрина под-каталогов (факт 4 требования: `course`, `product`, `methodology`, `kb-product` валидны и, вероятно, намеренны). Хардкод имён папок — проектно-специфичная проверка.
- Класс дефекта инцидента (битый YAML) уже ловится на error-уровне FR-120/FR-121 в `examples/` — это и блокирует публикацию. «7–8 мусорных каталогов в витрине» — отдельная UX-проблема организации контента, адресуется рекомендацией в writer-skill, не error-валидатором.
- BR-004: битый `examples/.doc-root.yaml` получил бы и parse-error, и warning «лишний root» — два сообщения на один дефект.

## Решение 5 — Q2: группа `CatalogErrorGroups` для FR-120/FR-121

**Решение:** находки FR-120…FR-123 классифицируются существующей группой **`content`** (`incorrects-content`). Паттерн группы `^(?:ERROR|WARNING)\s+.*\s+(?:missing|invalid|плейсхолдер|placeholder|фронтматтер|frontmatter)` уже матчит сообщения doc-root-проверок: `missing field: ...`, `invalid type for field ...`, `invalid yaml: ...`; подсказка FR-123 содержит `плейсхолдер`/`placeholder`. **Таксономия `_ERROR_GROUPS` не меняется**, новых групп не вводится.

## Решение 6 — AC-040: догфудинг — исключаем пути фикстур из обхода (вариант а)

**Решение:** фикстурные пути **исключаются из обхода** (включены в список Решения 1), а не чинятся. `ac-001-dogfood-clean-exit.sh` остаётся зелёным: в `content/` один `.doc-root.yaml` (primary), вложенных корней нет — догфудинг не краснеет даже без исключений; исключения защищают прогон на корне репозитория/`plugins/` (разработка, гипотетический hook).

**Почему не «чинить фикстуры» (вариант б):**
- Отрицательные фикстуры (`placeholder-leak`, `broken-link`, `unsupported-html`, `gramax-fixtures/*-broken`, `plugins/gramax/scripts/tests/fixtures/bad/`) **намеренно невалидны** — «починка» уничтожила бы их роль негативных тестов.
- Фикстуры продолжают валидировать валидатор напрямую: ac-*.sh и pytest `test_validate_structure.py` передают fixture-путь как корень (прямая инвокация, не рекурсивное обнаружение) — исключение из обхода на неё не влияет.
- Исключение по имени каталога не срабатывает (fixture-каталоги называются `bad`, `good`, `placeholder-leak` и т.п.) — нужен именно явный список путей.

## Решение 7 — версия плагина 4.5.0 (Minor) и разрешение на правку `marketplace.json`

**Разрешение:** этот ADR — разрешающий документ (прецедент ADR-0012 Решение 7, ADR-0019 Решение 9) на `metadata.version` → `"4.5.0"` в `.claude-plugin/marketplace.json` и текстовую (не структурную) правку `description` записи `gramax`, если Tech-writer сочтёт нужным упомянуть рекурсивное обнаружение/типизацию. `name`, `owner`, состав `plugins`, `source` неприкосновенны.

**Semver (ADR-0006): Minor.** Критерии Major (переименование, удаление skill, несовместимый `mcpServers`, смена структуры `marketplace.json`) не затронуты. Patch отклонён: новые error-находки меняют exit-поведение ранее «чистых» прогонов (вложенный битый `.doc-root.yaml` и `title` не-строкового типа раньше давали exit 0) — это функциональное изменение, не bug-fix-без-изменения-поведения. Находки — генуинные дефекты; известных потребителей у `validate_structure.py` нет (ADR-0012 G1) — покраснения существующего CI нет (дух NFR-001). Прецедент классификации новых error-проверок как Minor — ADR-0012 Решение 7 (4.2.0), ADR-0019 Решение 9 (4.4.0). `plugins/gramax/.claude-plugin/plugin.json`: `4.4.0` → `4.5.0` (не требует отдельного ADR).

## Consequences

**Положительные:**
- Класс дефекта инцидента 2026-08-13 (битый `.doc-root.yaml` во вложенных `examples/`) ловится до пуша, а не по жалобе разработчика Gramax — FR-120…FR-123 закрыты структурно.
- Диагностика больше не схлопывается до одного сообщения при невалидном YAML: битый `.doc-root.yaml` не глушит placeholder/links/orphans-находки того же каталога.
- «Одна находка на дефект» (BR-004) — структурная: parse-error с подсказкой поглощает placeholder того же токена; ownership вложенных root переиспользует существующую границу `in_scope=False`, не вводит post-hoc-дедуп.

**Отрицательные / trade-offs:**
- Строгость растёт: каталоги, ранее проходившие валидацию с `title: 4.21`/`title: yes`/вложенными битыми `.doc-root.yaml`, теперь краснеют. Смягчается ADR-0012 G1 (нет известных потребителей) и тем, что находки — генуинные дефекты.
- Каталоги с копиями `examples/` получают больше находок (каждый вложенный root валидируется полностью) — цена соответствия реальному поведению Gramax.
- «Мусорные catalog root в витрине» (7–8 на каталог) остаются недиагностируемыми валидатором (Решение 4) — UX-вопрос организации контента вне периметра.
- Прогон дорожает на полный обход дерева (вместо одного файла) — офлайн, на каталог потребителя доли секунды.

**Mitigations:**
- Исключения обхода — явный список (Решения 1/6): фикстурные пути не флагаются, догфудинг и `--full` suite остаются зелёными.
- Новые AC-036…AC-040 (suite `catalog-validator`) фиксируют регресс-якорь инцидента: AC-036 на до-FR-120 фикстуре даёт exit 0.
- CHANGELOG-маркер `Contract:` при изменении семантики `docRootRequiredFields` (прецедент ADR-0012 FR-041).

## Alternatives Considered

- Валидировать вложенные `.doc-root.yaml` только по признаку «наличие/парсинг», без полного suite (Решение 1) — отклонено: AC-039 требует «валидируется как отдельный root»; неполная валидация оставила бы классы дефектов вложенных каталогов невидимыми.
- Новый отдельный скрипт по образцу `validate_render.py` (ADR-0019 Решение 1) — отклонено: предмет — структура каталога (обнаружение root, типы полей `.doc-root.yaml`), родной для `validate_structure.py`; контент-слой уже отделён в `validate_render.py`.
- Чинить фикстуры вместо исключения путей (Решение 6, вариант б AC-040) — отклонено: отрицательные фикстуры намеренно невалидны, «починка» уничтожила бы негативные тесты.
- Warning с отдельным кодом для «extra root в служебной папке» (Решение 4) — отклонено: нет универсального критерия «служебной папки», риск ложных срабатываний на легитимных `examples/`, дубль-находка с parse-error (BR-004).
- Patch-версия 4.4.1 (Решение 7) — отклонено: новые error-находки меняют exit-поведение ранее чистых каталогов — функциональное изменение, Minor по прецеденту.
