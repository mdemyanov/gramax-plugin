# ADR-0016: Контракт формы ссылки на артефакт — резолвер гейта и временный протокол при расхождении с nauta

**Status:** Accepted
**Date:** 2026-08-13
**Plugin:** gramax / marketplace

## Context

Требование `content/30-requirements/2026-08-13-link-form-contract.md` (FR-077…FR-092) закрывает
находку сплошного аудита корпуса (RES-005): 103 из 136 код-спанов `content/*.md` — навигационные
отсылки, которые должны были быть markdown-ссылкой, а не путём-текстом. Три исполняемых probe
установили факты, на которые опирается это решение (established, не переизмеряю):

- Движок Gramax резолвит ссылку без расширения (`[X](doc)`) через инференс `.md`/`_index.md`;
  штатный редактор при пересохранении сам срезает `.md` для синтаксиса `XML` (наш каталог) —
  правило `plugins/gramax/skills/writer/SKILL.md:210` соответствует движку (RES-004).
- Оба живых валидатора каталога — `plugins/gramax/scripts/validate_structure.py` (наш) и
  `scripts/validate-content.py` (nauta, чужая территория) — требуют буквального `.exists()` без
  инференса и потому ложно считают такую ссылку битой (RES-004).
- Форма `content/<имя-каталога>/путь.md` не резолвится движком ни при каких условиях — чистый
  антипаттерн, не альтернативный синтаксис (RES-004, форма 8).
- Кросс-каталожная ссылка резолвится только по `../../<имя-папки>/...` с точно рассчитанным
  числом `../`, не по `code:` — `SKILL.md:213-220` («код-спан, не markdown-ссылка») верен по
  практическому эффекту (RES-006).

**Зависимость на ADR-0017 (объявлена, не решается здесь).** Ретракция кросс-каталожного
`code:`-рецепта в `references/doc-root-schema.md` — параллельная задача, закреплённая за
ADR-0017. Решения 1 и 5 этого ADR опираются на то, что практический вывод FR-085 (кросс-каталожная
ссылка остаётся код-спаном) сохраняется. Если ADR-0017 пересмотрит применимость самого код-спана
(не только рецепта через `code:`), Решения 1 и 5 требуют повторного разбора — это ADR не решает за
ADR-0017.

**Прецеденты.** Выбор severity для новых проверок — ADR-0012 Решение 2 (детерминированный дефект →
error, эвристика с риском ложных срабатываний → warning). Форма фиксации амендмента без правки уже
принятого ADR — ADR-0015 Решение 3 (тот же паттерн применён здесь: NFR-005 остаётся требованием
`SKILL.md`/резолвера, а не средством решить за ADR-0012/0015, чьи Решения не трогаются).

Детали реализации, контракт с Dev/DevOps/QA-author — в companion-статье
`content/40-architecture/2026-08-13-link-form-contract-design.md`. В этом документе — только
решения и их обоснование.

## Решение 1 — Резолвер: инференс расширения в общей точке `_collect_links` (FR-082, FR-081, FR-084, NFR-001, NFR-002)

**Решение:** 3-шаговый инференс расширения (по образцу `linkCreator._resolveHrefPath`, RES-004) —
литеральная цель → цель `+.md` → цель `/_index.md` — встраивается в **`_collect_links`**
(`plugins/gramax/scripts/validate_structure.py:286-313`), не отдельно в `check_broken_links`.
Причина размещения: обе проверки — `check_broken_links` (FR-048, error) и `check_orphans`
(FR-047, warning) — читают одно и то же поле `LinkRef.resolved`, вычисляемое `_collect_links`
один раз (строка 310). Правка только `check_broken_links` оставила бы `check_orphans` со старым
литеральным резолвом: входящая степень для любой будущей ссылки без расширения продолжила бы
считаться по несуществующему пути (`doc`, не `doc.md`) и не совпадала бы с ключом реальной статьи
в `incoming` — статья с корректной по FR-080 входящей ссылкой ошибочно осталась бы «сиротой».
Это не гипотетический риск: сегодня совпадения нет только потому, что все 60 существующих
внутренних markdown-ссылок уже пишутся с явным `.md` (RES-005) — первая же ссылка без расширения
проявила бы дефект. Единая точка правки устраняет его для обеих проверок одним изменением.

Инференс применяется **только** к цели без расширения `.md` — цель, уже оканчивающаяся на `.md`,
резолвится литерально, как сегодня (NFR-001: чисто ослабляющее изменение, 60 существующих ссылок
не меняют путь резолва).

**Антипаттерн (FR-081) остаётся ошибкой без отдельного кода.** Форма `content/section/doc.md`
уже несёт явное расширение → инференс к ней не применяется → ни литеральная попытка, ни она же
с довеском `_index.md` не находят файл (реальный путь — `<root>/section/doc.md`, не
`<root>/content/section/doc.md`, RES-004 форма 8) → `check_broken_links` продолжает поднимать
error. Проверено сценарием AC-010. Отдельный, специализированный детектор антипаттерна не
заводится — YAGNI: существующий механизм ловит его как частный случай генуинно битой ссылки,
дополнительный код добавил бы площадь без нового исхода.

**Граница вне каталога (FR-084) не требует нового кода.** Код-спан с путём никогда не попадает в
`_collect_links` — `_mask_code` вырезает inline-код до сканирования markdown-ссылок. Путь вне
`.doc-root.yaml`-каталога, упомянутый только в код-спане, не проверяется ни одной из двух проверок
уже сегодня, этой архитектурой, без изменений (AC-012 подтверждает существующее поведение, не
новое).

**NFR-002 (перф):** до 3 обращений `Path.exists()` на ссылку вместо одного — на масштабе корпуса
(52 файла, 68 markdown-ссылок) не измеримо для интерактивного использования. Числовой порог на
кратно большем каталоге — N/A, не измерено (см. companion-статью, «Открытые вопросы»).

## Решение 2 — Расхождение с `scripts/validate-content.py` (nauta): временный протокол `.md`-суффикса + апстрим-issue (FR-083)

**Факт, поднятый этим ADR, не зафиксированный явно требованием.** `check_broken_links` nauta (C9,
`scripts/validate-content.py:350-357`) — error, подключён к `check.sh --fast` на каждый коммит
(`main()`, безусловно). Тот же класс дефекта, что чинит Решение 1, но на территории, которую это
требование прямо выводит из scope. Последствие шире одноразовой миграции FR-091: `SKILL.md:210`
**уже сегодня** предписывает форму без `.md` — первая же корректно оформленная по этому правилу
NAV-ссылка, написанная любым автором (не обязательно частью миграции 103 код-спанов), красит
`check.sh --fast` немедленно, потому что nauta не делает инференса вовсе.

**Решение:**
1. Завести апстрим-issue в `tools-ai/nauta` (текст — companion-статья) — второй, отдельный дефект
   той же функции C9, по прецеденту уже заведённого issue №1 (маскирование fenced/inline-кода,
   2026-08-07, project-memory `project_nauta_migration_blocked_c9`). Тот же паттерн эскалации:
   «чинить в апстриме, не писать в чужой репозиторий руками».
2. **До релиза nauta с фиксом и пересинка этого репозитория** (`/nauta:sync-scripts`) — каждая
   markdown-ссылка, вносимая в `content/` **этого** репозитория (и результатом миграции FR-091, и
   любой органически новой NAV-ссылкой), пишется с явным `.md` (или `.../_index.md` для раздела).
   Это ровно форма, уже доказанно работающая для всех 60 существующих ссылок корпуса (0 битых,
   подтверждено независимым прогоном `validate-content.py`, RES-005) — нулевой добавочный риск.

Это **не отмена FR-080** и не решение SA поверх уже принятого BA-требования: FR-080 фиксирует
целевой канонический синтаксис (без расширения) и не требует обязательной ретро-миграции 60
существующих `.md`-ссылок — Решение 2 лишь откладывает **момент**, с которого новые ссылки этого
репозитория переходят на канонический синтаксис, до момента, когда это можно сделать не красня
`check.sh --fast`. `SKILL.md:210` (правило для внешних потребителей плагина) не меняется и не
противоречит этому — оно и резолвер плагина (Решение 1) уже согласованы (NFR-005). Расхождение
временное и локальное к тому, как **этот** репозиторий сам себя авторит, пока апстрим не
подтянется.

**Отклонено:**
- Блокировать миграцию FR-091 и вообще любые новые NAV-ссылки до релиза nauta — отклонено:
  прошлый апстрим-блокер (issue №1) не разрешён 5+ дней на момент этого ADR; блокировать
  bidirectional-linking (FR-089) и правило цитирования (FR-086) на неопределённый внешний срок
  подрывает саму цель этого требования сильнее, чем временный `.md`-суффикс.
- Править `scripts/validate-content.py` в этом репозитории — отклонено требованием (FR-083, чужая
  территория) и конвенцией репозитория.
- Симлинки/дублирующие файлы без расширения рядом с оригиналом — отклонено: физическое дублирование
  контента на каждую NAV-ссылку не масштабируется и создаёт новый источник рассинхрона.

## Решение 3 — Классификация NAV/SELF/SUBJECT (FR-077…FR-079): без нового гейта

**Решение:** классификация не становится ни блокирующей, ни предупреждающей автоматической
проверкой. Причина: из трёх тестов FR-077 (directionality, existence, scope) автоматизируемы
только два последних — existence и scope уже механичны и уже реализованы для markdown-ссылок
(`in_scope` в `_collect_links`). Directionality — эвристика по маркерным фразам («см.»,
«зафиксировано в» и т. п.) — не различает NAV от SUBJECT без неё: код-спан на существующий,
принадлежащий каталогу файл, упомянутый как предмет обсуждения (класс SUBJECT, 19 случаев в
корпусе, RES-005), синтаксически неотличим от NAV по одним только existence+scope. Регрессионный
тест AC-004 предметно защищает именно этот случай — принять существование+scope-only эвристику
означало бы систематически проваливать собственный regression guard требования.

По прецеденту ADR-0012 Решение 2 (детерминированный признак → error, эвристика с риском ложных
срабатываний → в лучшем случае warning, часто вообще не гейт) — directionality более эвристична,
чем orphan-детекция (у которой хотя бы граница cross-каталожных ссылок формализуема), и не
проходит even порог для warning-гейта. Финальная классификация остаётся решением автора в момент
письма и точкой ревью `/nauta:pm-review` — тот же locus, что BA уже выбрал для FR-086/FR-089
(AC-013, AC-016).

**Отклонено:** advisory-warning-гейт по existence+scope-подмножеству («похоже на NAV, проверьте
вручную») — не отклонено полностью, оставлено опциональным улучшением вне обязательного скоупа
этого ADR (companion-статья, «Открытые вопросы») — стоимость/пользу оценивает PM/Dev, не
предписывается здесь.

## Решение 4 — Цитирование и forward/back-linking (FR-086, FR-088, FR-089): не автоматизируется, усиливается чек-лист

**FR-086 (голая отсылка `FR-/AC-/NFR-/BR-NNN` без указателя на документ-источник).** Автоматизация
требует заранее знать, принадлежит ли конкретное упоминание `FR-NNN` документу, где оно написано,
или чужому — для этого нужен либо глобальный реестр владения номерами (не существует; тот же
пробел BA сама явно откладывает для `RES-NNN` как «не критично при текущем масштабе»), либо
эвристика по определению-паттерну (`**FR-NNN:**` жирным буллетом) — ненадёжная на прозе, не
следующей этому шаблону (user journey, таблицы), при масштабе в тысячи упоминаний (RES-005,
находка 6). Стоимость ложных срабатываний не оправдана без реестра.

**FR-088 (`путь:строка`, RECORD/POINTER).** Единственный реально найденный дефект
(`writer-consumer-rules.md:74`, off-by-one) — случай, где цитируемая строка **продолжает
существовать** в целевом файле (контент лишь сместился, не исчез). Механическая проверка
«строка N существует» не поймала бы именно этот наблюдаемый дефект — нужна проверка совпадения
содержимого, не номера строки, а это неформализуемо без структурированного контракта поверх
свободного текста.

**FR-089 (forward+back linking для новых статей).** Тот же класс: решение о том, «опирается ли
новая статья на предшественника» — семантическое, не выводится регуляркой из текста.

**Решение:** все три остаются процессными проверками `/nauta:pm-review` (тот же locus, что BA уже
выбрала в AC-013/AC-015/AC-016), без нового кода в `validate_structure.py`. Явный пункт в чек-лист
`pm-review` добавляется как процессное, не архитектурное изменение (companion-статья, Бриф для
PM/Dev). Триггер пересмотра: повторяющиеся пропуски этой проверки, дошедшие до `main` (эмпирический
сигнал), либо появление глобального реестра `FR-/AC-/NFR-/BR-NNN` по другой причине — тогда
автоматизация FR-086 станет дёшева заново.

## Решение 5 — Стратегия миграции 103 NAV-код-спанов (FR-091, FR-092)

**Решение:** Решение 2 снимает зависимость от апстрима (миграция пишет `.md`-суффикс) — миграция
не блокируется и может начинаться сразу после реализации Решения 1. Инструмент — standalone-скрипт
по прецеденту `plugins/gramax/scripts/migrate_mermaid.py` (ADR-0013 Решение 3/4): режим по
умолчанию — отчёт без мутаций, `--fix --yes` — мутация. Скрипт **пересканирует** корпус на
момент запуска тем же методом маскирования+классификации, что RES-005 (не полагается на
литеральные `file:line` из снимка RES-005 — этот ADR и параллельный ADR-0017 сами добавляют
контент в `content/`, после чего номера строк RES-005 устареют) и **прерывается без мутаций**, если
пересчитанное число NAV-кандидатов расходится с ожидаемым (103) без явного `--expect-count=N`.
Текст ссылки `[Название]` — механический дефолт из `title` целевого документа (frontmatter),
корректируемый Dev точечно там, где дефолт читается неудачно инлайн — закрывает единственный
немеханический шаг FR-091 дешёвым, не полностью ручным способом.

**Батчинг:** один PR, коммиты по подкаталогам doc-root (`00-project/adr` →
`10-domain/research` → `30-requirements` → `40-architecture` → `60-implementation`) — каждый
коммит независимо проверяется `check.sh --fast`/`--full`; не разбивается на несколько PR (чисто
механическая правка не выигрывает от фрагментации ревью). FR-092(b) (протухший путь) и FR-092(d)
(дрейф `путь:строка`) — ручные content-правки, а не вывод скрипта, включаются в коммит того
подкаталога, к которому относится правка.

**Регрессия vs намеренная правка при ревью:** отчёт скрипта (мигрировано / SELF / SUBJECT /
спорное) сверяется с ожидаемым числом (103 или пересчитанным эквивалентом) — основной сигнал;
`bash scripts/check.sh --fast`/`--full` по коду возврата — вторичный (число битых
ссылок/сирот не должно вырасти).

**Отклонено:** одна большая правка руками без инструмента — отклонено, 103 инстанса с
идентичной трансформацией не оправдывают ручной труд и риск опечатки на масштабе; несколько
отдельных PR — отклонено, не даёт ревью-выигрыша при чисто механической правке.

## Consequences

**Positive:**
- Единая точка резолва (Решение 1) закрывает будущий скрытый дефект `check_orphans`, не только
  явную жалобу FR-082/FR-048 — устраняется целый класс, а не один симптом.
- Расхождение с nauta (Решение 2) явно зафиксировано и компенсировано, а не оставлено молчаливым
  риском для первой же корректно оформленной ссылки — избегает повторения сценария issue №1
  (блокировка на неопределённый срок).
- Классификация и цитирование (Решения 3–4) не обрастают хрупкими эвристическими гейтами, дающими
  ложную уверенность — граница механичного/человеческого проведена явно и обоснованно.
- Миграция (Решение 5) безопасна к повторному запуску и к дрейфу строк, вызванному самими ADR-0016/
  ADR-0017.

**Negative / trade-offs:**
- Временный `.md`-суффикс (Решение 2) — второй, отличный от `SKILL.md:210`, синтаксис для
  собственного корпуса на неопределённый срок (до релиза nauta) — требует явного упоминания в
  companion-статье, иначе выглядит как непоследовательность.
- Директионность классификации (Решение 3) и цитирование (Решение 4) остаются человеческим
  процессом — тот же риск пропуска на ревью, что у любой чек-лист-проверки, не устранённый этим
  ADR.
- Скрипт-мигратор (Решение 5) — новая процедурная поверхность, которую нужно поддерживать
  (аналогично уже принятому дублированию обхода дерева `migrate_mermaid.py`, ADR-0013).

**Mitigations:**
- Апстрим-issue (Решение 2) даёт путь к устранению временного протокола, не постоянному
  дублированию конвенций.
- `--expect-count` guard (Решение 5) и report-first-по-умолчанию режим предотвращают тихое
  неполное или избыточное применение миграции.

**Semver (ADR-0006):** Minor — Решение 1 чисто ослабляет существующую error-проверку (не может
покрасить ранее зелёный каталог, симметрично классификации ADR-0012 Решение 1); никакого нового
JSON-контракта не вводится. Точный номер версии — решает PM/Dev порядком слияния (прецедент
ADR-0013). `plugins/gramax/CHANGELOG.md` получает запись `Contract:` по требованию NFR-004, хотя
`gramax-tags.json`/`gramax-catalog-rules.json` не меняются — контрактная поверхность здесь шире
двух JSON-файлов (само поведение резолва — часть публичного контракта валидатора).

## Alternatives Considered

- Дублировать инференс отдельно в `check_broken_links`, не трогая `_collect_links` — отклонено:
  оставляет `check_orphans` со старым резолвом, воспроизводя тот же класс дефекта для будущих
  ссылок без расширения (Решение 1).
- Блокировать FR-091/FR-086/FR-089 до релиза nauta с фиксом — отклонено: неопределённый внешний
  срок (issue №1 не разрешён 5+ дней), блокирует ядро цели требования (Решение 2).
- Патчить `scripts/validate-content.py` в этом репозитории — отклонено требованием и конвенцией
  репозитория (Решение 2).
- Автоматический (advisory или блокирующий) гейт на классификацию NAV/SELF/SUBJECT по
  existence+scope без directionality — отклонено: систематически проваливает собственный
  regression guard требования (AC-004) на классе SUBJECT (Решение 3).
- Автоматизация проверки голой отсылки `FR-NNN` (FR-086) через эвристику по bold-bullet-паттерну —
  отклонено: ненадёжна без глобального реестра владения номерами, цена ложных срабатываний высока
  на масштабе тысяч упоминаний (Решение 4).
- Механическая проверка «строка N существует» для FR-088 — отклонено: не ловит единственный
  реально наблюдаемый дефект (контент сместился, номер строки остался существующим) (Решение 4).
- Один большой ручной PR или несколько мелких PR для миграции корпуса — отклонено в обе стороны:
  ручной труд не оправдан на 103 идентичных трансформациях; фрагментация на несколько PR не даёт
  ревью-выигрыша при чисто механической правке (Решение 5).
