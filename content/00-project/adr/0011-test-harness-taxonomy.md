# ADR-0011: Таксономия test harness tests/gramax и гейт doc-paths

**Status:** Accepted
**Date:** 2026-08-09
**Plugin:** gramax / marketplace

## Context

`tests/gramax/` держит шесть suite. Два (`orphan-references`, `nauta-integration`) зелёные и
подключены к `bash scripts/check.sh --full`. Четыре (`remove-diagram-skills`,
`routing-mermaid-drawio`, `mermaid-file-based`, `diagram-on-demand`) красные (31/59 упавших
ассертов) и не подключены ни к чему — гниют начиная с релиза, для которого писались.

Разбор красных suite показал три разные природы падений в одном каталоге: версионные пины на
ушедшую версию (свидетельство приёмки), устаревшие ассерты на синтаксис (то же), реальные
дефекты v4.1.0. Смешение мешает отличить исторический факт от того, что нужно чинить сейчас.

Требование [Наведение порядка в test harness gramax и вычистка устаревших docs-путей](../../30-requirements/2026-08-09-test-harness-taxonomy-and-doc-paths.md)
специфицирует согласованный на брейншторме дизайн в терминах FR/AC и поручает SA формализовать
четыре архитектурных решения плюс два побочных: таксономию `tests/gramax/`, ретировку
невыполнимого AC, точные regex sunset-registry, границу гейта `doc-paths`, формат агрегатора
новых suite, разрешение на правку `metadata.version` в корневом `marketplace.json`.

Предшествующий контекст: ADR-0006 (semver-policy, Active), ADR-0008 «Решение 7» (прецедент — ADR
как разрешающий документ на правку `marketplace.json`), ADR-0009/ADR-0010 (история skill'ов,
покрытых архивируемыми suite).

## Решение 1 — таксономия `tests/gramax/`: архив vs живой suite

**Решение:** `remove-diagram-skills/`, `routing-mermaid-drawio/`, `mermaid-file-based/`
переезжают `git mv` в `tests/gramax/archive/<suite>/` без правки содержимого (BR-001).
`diagram-on-demand/` удаляется целиком `git rm -r`, не архивируется. `plugin-contract/` и
`doc-paths/` — новые живые suite, подключаются к `--full`.

**Критерий отнесения suite в архив (для будущих релизов):** природа ассерта, не имя suite и не
факт падения.

| Признак ассерта | Природа | Судьба |
|---|---|---|
| Сравнивает с литеральным значением, привязанным к конкретному релизу (версионный пин `== "2.0.0"`, синтаксис, который был каноническим на момент приёмки) | Свидетельство приёмки — истинно было на момент X, не обязано оставаться истинным дальше | Архив |
| Проверяет инвариант, не зависящий от номера версии (структура файла, наличие секции, отсутствие устаревшего синтаксиса как класса, а не конкретной строки) | Действующий контракт — обязан выполняться при любой будущей версии | Живой suite |
| Покрывает функциональность, которой больше нет в продукте ни в каком виде (skill удалён по ADR, а не переименован/расширен) | Свидетельство о прошлом без предмета проверки в настоящем | Удаление (`git rm`), не архив |

Suite целиком относится к архиву, если **все** его ассерты природы «свидетельство приёмки»;
живые ассерты того же suite (роутинг, формат тега, структура справочника) выделяются в
`plugin-contract` **до** переезда — это и есть работа FR-006…FR-015. `diagram-on-demand`
архивированию не подлежит: он не расщепляется на живую/архивную часть, потому что вся
покрываемая им функциональность (внутренние drawio-скрипты, `diagrams`/`diagram-on-demand`
skills) удалена ADR-0008 без остатка — архивный suite о полностью удалённом предмете был бы
свидетельством о нуле, не о факте. Факт приёмки уже зафиксирован в
[Acceptance: diagram-on-demand](../../60-implementation/acceptance/2026-05-08-diagram-on-demand-acceptance.md); история — в
git log. Дублировать это в неисполняемом suite — не документация, а балласт.

**Почему версионные пины остаются литеральными (`==`), не переводятся в `>=` (FR-003, BR-001):**
`>=` превращает утверждение «на момент версии 2.0.0 формат тега был таким» в утверждение «версия
не меньше 2.0.0» — то есть проверку текущего состояния под видом исторической записи. Такой
suite при каждом будущем bump молчаливо продолжал бы «проходить», даже когда контракт, который он
описывал, давно заменён (drawio-тег дважды менял синтаксис между 2.0.0 и 4.1.0) — зелёный результат
перестаёт что-либо удостоверять. Литеральный пин фиксирует «это было верно именно тогда» и не
предполагает повторного запуска — что и требует BR-001 (append-only, suite не запускается).

**Trade-offs:**
- Архив не ловит регрессию в зоне, которую раньше покрывал (не нужно — контракт той зоны
  заменён; регрессию по новому контракту ловит `plugin-contract`).
- Риск, что кто-то «поправит» архив из добрых намерений (обновит пин до текущей версии) —
  закрыт явным BR-001 + декларацией в `archive/README.md` («не редактировать, не запускать, не
  считать в отчётах»), а не техническим барьером; это осознанный выбор в пользу простоты
  (git-history уже даёт техническую защиту от потери, а не от правки).
- `archive/mermaid-file-based/verify.sh` — единственное разрешённое исключение из
  «архив не редактируется»: добавляется одним коммитом с переездом (FR-003, FR-015), дальше
  архив, включая сам `verify.sh`, заморожен целиком.

## Решение 2 — ретировка AC «поле `skills` в `plugin.json`» и процедура ретировки

**Решение:** `plugin-contract` не содержит ассерта на поле `skills` в `plugin.json` (FR-012).
Обоснование фиксируется в `tests/gramax/archive/README.md` (FR-002), не как код ассерта.

**Частный случай:** `routing-mermaid-drawio/ac-014` требовал присутствия поля `skills` в
`plugin.json`. Независимая проверка SA (2026-08-09, дополняет замер PM того же дня) по всем
установленным плагинам в `~/.claude/plugins/cache`:

```
find ~/.claude/plugins/cache -name plugin.json -path '*.claude-plugin*' | wc -l   → 53 файла
… уникальных имён плагинов (marketplace/name)                                    → 22
… файлов с top-level полем "skills"                                              → 0
```

Ни один `plugin.json` (53 файла, 22 разных плагина, включая `gramax` 4.1.0) поля `skills` не
несёт. Claude Code обнаруживает skills автоматически по каталогу `skills/` — декларативное поле
не читается рантаймом. AC опиралось на ложную посылку и никогда не могло стать выполнимым:
не «пока не реализовано», а «нечего реализовывать». (Расхождение с числом PM — «20» против
измеренных здесь «22» — объясняется тем, что кэш плагинов растёт со временем; направление
результата — «поле нигде не встречается» — то же самое.)

**Процедура ретировки AC** (обобщение за пределы этого случая — применимо к любому будущему AC,
который не зеленеет годами не из-за недоделанной реализации, а потому что сама предпосылка
неверна):

1. **Триггер.** AC систематически падает, и разбор показывает: падение не о том, что артефакт
   не создан, а о том, что описанный артефакт не существует и не должен существовать ни в одной
   версии системы, на которую опирается требование.
2. **Обязательное измерение.** Ретировка не принимается на слово. Нужна воспроизводимая проверка
   (grep/сравнение/выборка) с зафиксированным охватом (что проверено, сколько объектов, когда) —
   как в примере выше. Пустое место вместо измерения — не ретировка, а недоработка.
3. **Куда пишется.** Два места, не одно:
   - README архива/suite (`archive/README.md` для этого случая) — что ретировано, откуда взят
     AC, какая посылка была ложной, результат измерения;
   - ADR — когда ретировка сама является архитектурным решением (меняет, что именно
     `plugin-contract` осознанно не проверяет — FR-012). Если ретировка не затрагивает
     архитектуру (частный AC оказался опечаткой номера, дублем другого AC) — README suite +
     заметка QA-author/PM достаточны, ADR не требуется.
4. **Кто санкционирует.** SA — когда ретировка меняет состав архитектурно значимой проверки
   (как здесь: `plugin-contract` — новый живой suite, его состав есть архитектурное решение).
   Для непринципиальных случаев — QA-author документирует, PM подтверждает в review.
5. **Чем ретировка отличается от смягчения ассерта.** Смягчение меняет проверку на более
   слабую версию того же по смыслу утверждения (например, `grep -q '"skills"'` → `grep -qi
   'skills'` без анкоринга), пока тест не позеленеет, — покрытие тихо эрозирует, предмет
   проверки формально сохраняется. Ретировка **убирает** ассерт целиком и явно документирует,
   что сама проверяемая посылка была неверна — с воспроизводимым измерением, которое любой
   несогласный читатель может перепрогнать и оспорить.
6. **Защита от злоупотребления.** Ретировка без приложенного, перепроверяемого измерения —
   не ретировка, а скрытое удаление. Требование к воспроизводимости (шаг 2) — единственный
   барьер против использования этой процедуры для «тест мешает — уберём».

## Решение 3 — форма паттернов `sunset-registry.txt`

**Решение:** паттерн реестра опознаёт артефакт по пути или по способу вызова, никогда по
голому слову. Три новые записи (по одной на артефакт, каждая объединяет path-форму и
invocation-форму через альтернацию):

```
skills/diagrams([^a-zA-Z0-9-]|$)|gramax:diagrams([^a-zA-Z0-9-]|$)
skills/diagram-on-demand([^a-zA-Z0-9-]|$)|gramax:diagram-on-demand([^a-zA-Z0-9-]|$)
plugins/claude-mermaid([^a-zA-Z0-9-]|$)
```

Класс `([^a-zA-Z0-9-]|$)` — обязательная граница после имени артефакта: следующий символ не
буква/цифра/дефис, либо конец строки. Без границы path-форма всё ещё частично голая: `skills/
diagrams` — подстрока `skills/diagrams-export`, а `gramax:diagrams` — подстрока
`gramax:diagrams-export`. Граница отсекает продолжение идентификатора дефисом, но пропускает
`/`, кавычку, конец строки и т.п.

**Замер обеих сторон** (`grep -rnE`, `SEARCH_PATHS = plugins scripts tests CLAUDE.md AGENTS.md
README.md`, HEAD = c6f15ec, выполнено SA 2026-08-09):

*Ловит удалённое (позитив, до архивирования — реальные текущие вхождения в
`remove-diagram-skills/`, `diagram-on-demand/`, `routing-mermaid-drawio/`, которые переедут в
архив/удалятся):*


**Ограничение порядка (подтверждено измерением).** `plugins/claude-mermaid(...)` пока даёт 2
реальных попадания в `scripts/check.sh:39` и `:75` — мёртвые guard'ы для удалённого в v3.0.0
submodule, которые убирает FR-020. Если FR-013 (расширение реестра) закоммитить раньше FR-020
(очистка `check.sh`), промежуточный коммит красный вопреки NFR-001. Один из двух порядков
обязателен: FR-020 первым коммитом, либо FR-020+FR-013 одним коммитом. Раздельный коммит
«сначала FR-013» недопустим.

**Trade-off:** квалифицированная форма не ловит голое упоминание артефакта в прозе без
пути/вызова (например, гипотетический будущий текст «skill назывался просто diagrams»). Это
осознанно: цель реестра — остаточные ссылки, которые всё ещё что-то делают или на что-то
указывают (путь, вызов), а не любое упоминание имени в истории; для исторической прозы служат
уже существующие исключения `CHANGELOG.md` / `content/00-project/adr/` / `docs/` в `EXCLUDE_RE`.

## Решение 4 — политика `docs`-путей в `content/` и граница гейтов

**Решение:** критерий классификации записи — **роль предложения**, не каталог документа и не
факт присутствия строки `docs/...`.

| Роль | Определение | Действие |
|---|---|---|
| POINTER | Предложение приглашает читателя перейти по пути дальше (trace-шапка, футер «Связанные артефакты», ссылка «см. …») | Чинится на новый путь (FR-025) |
| RECORD | Предложение описывает факт на момент решения/находки — само является историческим утверждением, не навигацией | Остаётся дословно, защищено allowlist (FR-026) |

Одна и та же строка `docs/adr/0006-...` может быть POINTER в футере ADR («затрагивает:
`docs/adr/0006-...`» — приглашение перейти) и RECORD в теле dispозиции («на HEAD=X упоминание
было найдено по адресу `docs/adr/0006-...`» — констатация факта, который был верен в момент
находки). Критерий не про то, где лежит файл, а про то, что делает конкретное предложение.

**Две формы allowlist (FR-026) и почему whole-file — не дыра:**

- `file:line — причина` — точечная защита одной строки; гейт построчно сверяет содержимое с
  ожидаемым паттерном (FR-027) и падает при рассинхроне. Дыры здесь нет структурно: allowlist не
  освобождает файл от проверки, освобождает конкретную зафиксированную строку.
- `file — причина` — защита файла целиком, но **не произвольного**: применима только к
  документам, чья *тема* — сама миграция путей (это требование, будущий ADR-0011, будущие
  отчёты QA-runner о реализации). Такой документ не содержит POINTER-предложений: он либо
  таблица соответствия старого/нового пути, либо диспозиция переезда — по критерию «роль
  предложения» весь документ целиком RECORD, whole-file форма лишь констатирует то, что уже
  верно на уровне отдельных строк. Она не расширяет то, что allowlist разрешает, а сокращает
  число строк, которые для документа этого типа пришлось бы перечислять по одной — сотни
  вхождений `docs/...` в таблице соответствия иначе потребовали бы сотен точечных записей ради
  одного и того же вывода. Гейт для такой записи не сканирует файл построчно — что корректно:
  сканировать нечего проверить *против* (весь файл — не POINTER).
  Граница защиты этой формы — тип документа, определённый на момент внесения записи в
  allowlist, не любой будущий файл, который кто-то захочет туда добавить: расширение whole-file
  списка — редактирование allowlist.txt, видимое в diff и требующее того же ревью, что и любая
  другая правка гейта.

**Граница между `doc-paths` и `nauta-integration/ac-007` (BR-003) — два гейта, не один:**

| | `doc-paths` (новый) | `nauta-integration/ac-007` (существующий, не трогается) |
|---|---|---|
| Область сканирования | `content/**` | `plugins`, `tests`, корневые `CLAUDE.md`/`AGENTS.md`/`README.md` |
| Природа находок | POINTER/RECORD в документах о решениях и требованиях | Остаточные code-level ссылки после миграции задачи 6 |
| Жизненный цикл | Растёт: новые документы о самой миграции легитимно называют старые пути и требуют новых allowlist-записей | Одноразовая проверка полноты миграции; после зелёного прогона не должна расти |
| Автор новых правил | SA/BA, пишущие про содержание миграции | QA-author/Dev, доводящие code-level ссылки до нуля |

Разделение — не искусственное: `content/` и код (`plugins`/`tests`/корневые файлы) обслуживают
разных читателей с разной терпимостью к историческим упоминаниям (документ о решении обязан
уметь сказать «путь был таким», код и агентские инструкции — нет, там любой `docs/`-путь обязан
быть либо рабочим, либо отсутствовать). Объединение в один гейт заставило бы один агрегатор
понимать обе политики исключений сразу и создало бы риск, что allowlist-механизм `doc-paths`
(RECORD-документы) незаметно замаскирует code-level остаточную ссылку, которую `ac-007` обязан
ловить безусловно. **Куда добавлять новое правило:** если путь живёт в `content/` — запись в
`tests/gramax/doc-paths/allowlist.txt`; если путь живёт в коде/тестах/корневых документах —
паттерн `nauta-integration/ac-007-no-stale-doc-paths.sh` (правит его владелец задачи 6, вне
периметра этого требования).

## Решение 5 — формат агрегатора `run.sh` (закрытие открытого вопроса №3)

**Решение:** `plugin-contract/` и `doc-paths/` — плоская структура, без подкаталогов на шесть
категорий проверок. Каждая категория из FR-006…FR-011 — один или несколько файлов
`ac-*.sh` прямо в каталоге suite, сгруппированных именем файла (`ac-00N-<тема>.sh`), не
директорией. `run.sh` — тот же паттерн, что `nauta-integration/run.sh`: glob `ac-*.sh` в своём
`SCRIPT_DIR`, цикл, счётчики `pass`/`fail`, список упавших, `exit 1` при `fail > 0`. `doc-paths`
переиспользует тот же скелет; проверка свежести allowlist (FR-027) — отдельный `ac-*.sh` на
фикстуре, не логика, вшитая в `run.sh` — так она тестируется и читается наравне с остальными AC.

**Обоснование:** шесть категорий FR-006…FR-011 — это ~10-15 файлов суммарно, не десятки;
прецедент `nauta-integration/` (8 `ac-*.sh` в одном каталоге + `lib/`) и `orphan-references/`
(один `run.sh` без подкаталогов вовсе) уже показывают, что плоская структура читается на этом
масштабе без навигационных проблем. Подкаталоги по категориям добавили бы косвенность (нужно
открыть директорию, чтобы понять, что внутри) без выигрыша, который проявился бы только при
существенно большем числе файлов. Соответствие категории AC документируется таблицей в
`plugin-contract/README.md` (по образцу `routing-mermaid-drawio/README.md`), не деревом
каталогов.

**Trade-off:** если `plugin-contract` в будущем разрастётся далеко за первоначальные шесть
категорий, плоская структура станет менее читаемой; ADR не запрещает будущую SA-инициированную
реорганизацию в подкаталоги — фиксирует только стартовое состояние.

## Решение 6 — разрешение на правку корневого `marketplace.json` (bump 4.1.1)

**Решение:** данный ADR — разрешающий документ на правку `.claude-plugin/marketplace.json`
исключительно поля `metadata.version` → `"4.1.1"` (FR-023). Никакое другое поле не меняется:
`name`, `owner`, структура и содержимое `plugins` (включая `name`, `source`, `description`
записи `gramax`) — неприкосновенны в рамках этого решения.

**Цепочка разрешения (по прецеденту ADR-0008 «Решение 7»):** красная линия CLAUDE.md требует
ADR как разрешающий документ для правки корневого `marketplace.json`. ADR-0006 (Active)
устанавливает семантику версионирования; ADR-0008 «Решение 7» показал, что сам факт наличия
ADR, документирующего конкретную правку версии, удовлетворяет красную линию без отдельного
дополнительного PM sign-off. Этот ADR-0011 — тот же паттерн для 4.1.1: документирует правку до
её выполнения Dev. Дополнительно получена явная санкция пользователя 2026-08-09 (BR-002) —
избыточна относительно строгого прочтения красной линии (ADR уже достаточен), но фиксируется
здесь как второй независимый источник разрешения для файла с публичным контрактным статусом.

**Semver-классификация 4.1.1 (по ADR-0006):** Patch, не Minor и не Major. Фиксы FR-017…FR-021 —
миграция синтаксиса тега в двух уже существующих файлах, добавление WARNING, удаление мёртвых
guard'ов — исправляют расхождение с уже задокументированным поведением, не меняют публичный
API/skill-набор и не удаляют ничего, на что мог полагаться пользователь. Это ровно определение
Patch из ADR-0006 («bug fix, исправление описания без изменения функциональности»). Отсюда —
только `metadata.version` меняется; `description` записи `gramax` не требует обновления (в
отличие от прецедентов 2.0.0/3.0.0, где менялся набор skill'ов и описание было обязано это
отразить).

**Trade-off:** проверяемость границы разрешения (AC-024) оставлена структурной, не
процедурной — Dev не может «случайно» задеть другое поле незамеченным, потому что AC-024
проверяет остальные поля побайтово равными текущим значениям; это превращает NFR-005 в
исполняемый гейт, а не в договорённость на словах.

## Consequences

**Положительные:**
- Test harness перестаёт врать о состоянии плагина: `--full` включает 4 suite вместо 2, красный
  результат реально блокирует релиз.
- Критерий «природа ассерта» (Решение 1) переносится на будущие релизы без повторного
  брейншторма — при следующем major/minor bump понятно, что уходит в архив, а что остаётся
  живым.
- Процедура ретировки AC (Решение 2) закрывает конкретный случай и даёт репозиторию
  многоразовый механизм для будущих ложных предпосылок в AC, с барьером против злоупотребления.
- Квалифицированные regex (Решение 3) закрывают открытый вопрос №1 требования и находят
  дополнительный false positive (AGENTS.md), не выявленный на этапе BA.
- Граница `doc-paths` / `ac-007` (Решение 4) даёт читателю однозначный ответ, куда класть новое
  правило про устаревший путь.

**Отрицательные / trade-offs:**
- Архив — исторический балласт в репозитории (небольшой: 3 каталога, суммарно счётные файлы),
  принят осознанно взамен потери привязки к релизу при `>=`-пинах.
- Whole-file форма allowlist (Решение 4) требует дисциплины при добавлении новых записей —
  граница держится на ревью, не на автоматической проверке типа документа.
- Плоская структура `plugin-contract`/`doc-paths` (Решение 5) не масштабируется бесконечно;
  явно не заблокирована будущая реорганизация, если категорий станет существенно больше.
- Regex Решения 3 проверены на текущем `HEAD` и текущем grep-бинарнике окружения SA (ugrep 7.5.0
  в режиме extended regex); QA-author обязан перепроверить оба направления на CI-окружении при
  реализации (это явно оставлено требованием на уровень QA-author, не переиспользуется здесь
  как готовый гарантированный результат).

**Mitigations:**
- BR-001 + `archive/README.md` — единственная защита архива от «улучшающей» правки; технической
  защиты нет осознанно (см. Решение 1).
- Ограничение порядка FR-020→FR-013 явно зафиксировано и подтверждено измерением — предотвращает
  промежуточный красный коммит.
- AC-024 делает границу правки `marketplace.json` (Решение 6) исполняемой, не декларативной.

## Alternatives Considered

- **`>=`-пины вместо литеральных в архиве** — отклонено (Решение 1): превращает свидетельство
  приёмки в проверку текущего состояния, теряет привязку к релизу.
- **Архивировать `diagram-on-demand` вместо удаления** — отклонено (Решение 1): вся покрываемая
  функциональность удалена без остатка, архивный suite о нуле не документирует ничего сверх уже
  существующей приёмки и git log.
- **Смягчить AC про поле `skills` вместо ретировки** — отклонено (Решение 2): смягчение прячет
  ложную посылку под ослабленной формулировкой; ретировка с измерением делает решение
  прозрачным и оспоримым.
- **Голые слова `diagrams`/`diagram-on-demand`/`claude-mermaid` в реестре** — отклонено
  (Решение 3): ломает сегодня зелёный `orphan-references` (5 попаданий в `nauta-integration`),
  ложно триггерится на легитимную прозу (`staging.md:30`, `drawio.md:60`) и на будущий
  `doc-paths/allowlist.txt`.
- **Один общий гейт вместо `doc-paths` + `ac-007`** — отклонено (Решение 4): разная область
  сканирования, разный жизненный цикл (растущий vs одноразовый), разный автор правил; общий
  агрегатор был бы обязан понимать обе политики исключений одновременно.
- **Подкаталоги по шести категориям для `plugin-contract`** — отклонено (Решение 5): выигрыш
  проявляется только при существенно большем числе файлов, чем текущие ~10-15; плоская
  структура соответствует прецеденту `nauta-integration`/`orphan-references`.
- **Bump `marketplace.json` без ADR, только с санкцией пользователя** — отклонено (Решение 6):
  красная линия CLAUDE.md требует именно ADR как разрешающий документ; санкция пользователя —
  дополнительна, не заменяет ADR.
