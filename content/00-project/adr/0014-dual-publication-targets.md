# ADR-0014: Два независимых таргета публикации — публичный GitHub и внутренний GitLab-каталог

**Status:** Accepted
**Date:** 2026-08-11
**Plugin:** marketplace

## Context

Репозиторий обслуживает две разные аудитории одним содержимым. Публичная — пользователи Claude
Code marketplace, устанавливающие плагин через `/plugin marketplace add mdemyanov/gramax-plugin`
(GitHub). Внутренняя — читатели корпоративного Gramax Enterprise Server (GES), которым нужен тот
же `content/` как отрендеренный каталог документации.

Отдать эту роль одному GitHub-репозиторию нельзя физически: workspace GES привязывается к
одному git-хосту через `git.source`:

```yaml
git:
  source:
    type: GitLab
    url: <внутренний-хост>
```

GitHub-репозиторий источником такого workspace быть не может — хост фиксирован в конфиге GES
(`nau-gramax-manager/workspace.yaml`), не выбирается per-репозиторий.

Публикуется весь репозиторий, не только `content/`: Gramax не требует, чтобы `.doc-root.yaml`
лежал в корне. Подтверждено практикой: (а) `repositories/tools-ai/nsmp-plugin.yaml` в GES несёт
`mainBranch: public`, а ветка `public` репозитория `tools-ai/nsmp-plugin` держит в корне `src/`,
`scripts/`, `.claude-plugin/`, `docs/` — `.doc-root.yaml` лежит в `content/`, и GES это рендерит;
(б) из шести проверенных репозиториев-потребителей (`gramax-user-docs`, `moex`, `tsn-assistant`,
`process_design`, `mango-cti-rest`, `nsmp-plugin`) все шесть держат `.doc-root.yaml` в `content/`,
ни один — в корне. Значит зеркалировать нужно репозиторий целиком, не вычленять поддерево.

Решение принято и механизм уже выполнен — этот ADR фиксирует его постфактум.

## Decision

Два независимых git-таргета публикации с разными ролями. Редактирование существует только на
одном из них.

| Компонент | Роль | Ответственность | Границы |
|---|---|---|---|
| GitHub `mdemyanov/gramax-plugin` (`origin`) | Источник правды, канал distribution | canonical история; пользователи ставят плагин через `/plugin marketplace add` | Единственное место, где происходит редактирование |
| Внутренний GitLab `tools-ai/gramax-plugin` (`internal`) | Read-only витрина | источник каталога для GES workspace | Редактирования не принимает; получает только то, что уже прошло `origin` |
| GES | Рендерер | читает `content/` по `.doc-root.yaml`, строит навигацию для внутренних читателей | Ничего не пишет обратно в git |
| Локальная `main` | рабочая копия | upstream — только `origin/main` | обычный `git push`/`git pull` не задевает `internal` |

**Механизм (уже выполнен).** Второй git remote `internal`, публикация обновлений — ручной `git
push internal main`. Репозиторий создан через GitLab push-to-create, приватный; на момент этого
ADR `internal/main` синхронизирован с `origin/main` на коммите `99ce3a5`. Upstream локальной
`main` сознательно оставлен на `origin/main`: если бы `internal` стал upstream (или единственным
push-target через `set-url`), рутинный `git push` без параметров начал бы неявно уезжать во
внутренний контур — риск не столько утечки (репозиторий приватный), сколько потери контроля над
тем, что именно и когда туда попадает.

**Опциональный вариант на будущее, не принятый сейчас:** multi-push remote
(`git remote set-url --add --push`), отправляющий один `git push` в оба таргета одной командой.
Не выбран как основной механизм, потому что тогда во внутренний контур автоматически уезжает и
любой force-push — а ручной `git push internal main` даёт возможность придержать публикацию
(например, до готовности релиза) независимо от того, что уже ушло в `origin`.

### Интеграционная точка: как GES получает контент

| Точка | Механизм | Контракт | Поведение при рассинхроне |
|---|---|---|---|
| GES ← `internal` (GitLab) | GES клонирует/тянет `tools-ai/gramax-plugin`, `mainBranch: main` | `.doc-root.yaml` — в `content/` (не в корне репозитория); GES рендерит только поддерево `content/`, остальные каталоги (`plugins/`, `docs/`, `.claude-plugin/`) для витрины не значимы | Витрина отстаёт от `origin` до следующего `git push internal main` — **допустимое состояние, не ошибка**. Автоматического алертинга о рассинхроне нет |
| `origin` → `internal` | `git push internal main`, вручную, инициирует владелец репозитория | Append истории; отдельной политики anti-force-push на этот remote не задано — сознательный минимализм механизма | N/A — обновление триггерится человеком, не событием |

**Инвариант, который несёт двойную нагрузку.** `.doc-root.yaml` живёт в `content/`, не
переезжает в корень. Тест `tests/gramax/nauta-integration/ac-003-doc-root-contract.sh` уже держит
этот инвариант для nauta-контракта; с этим ADR он же становится условием, при котором внутренняя
витрина вообще способна рендериться. Рефакторинг структуры репозитория, который переместит
`.doc-root.yaml` без учёта этого факта, молча сломает GES-витрину — тест это поймает раньше, чем
кто-то заметит по жалобе внутренних читателей, но только если разработчик знает, что тест теперь
защищает две вещи, а не одну.

**Read-only — политика, не техническое ограничение.** Внутренний контур не принимает
редактирование сегодня по договорённости, не потому что GitLab технически не может принять push
из Gramax UI. Если однажды редакторы начнут править контент через Gramax UI на внутренней
витрине — это отдельное архитектурное решение: нужен новый ADR и гейт DevSecOps на обратный поток
(риск — утечка внутренних хостов и имён клиентов в публичный GitHub при последующей синхронизации
изменений назад в `origin`).

**Маскирование хоста.** Имя внутреннего GitLab-хоста не попадает в файлы `content/`, `docs/`,
`README.md` и любые другие публичные файлы этого репозитория — по прецеденту
`docs/onboarding-nauta.md`. Путь `tools-ai/gramax-plugin` не секрет и не маскируется.

### Что нужно вне этого репозитория, чтобы витрина заработала

Регистрация в GES — отдельный шаг, не выполняемый этим ADR и не в этом репозитории: файл
`repositories/tools-ai/gramax-plugin.yaml` (по образцу соседнего `nsmp-plugin.yaml`, но
`mainBranch: main`, не `public` — у этого репозитория нет раздельных веток) плюс запись
`gramax-plugin` в секции `tools-ai` файла `workspace.yaml`. Делается PR-ом в `nau-gramax-manager`.
До выполнения этого шага `internal`-remote существует и синхронизирован, но GES его не видит.

## Alternatives Considered

- **`git subtree split` — зеркалировать только `content/`.** Отклонено: требует отдельного
  скрипта публикации, теста на идемпотентность сплита и разбирательств при расхождении историй
  двух деревьев. Выигрыша нет — лишние папки (`plugins/`, `docs/`) каталогу в GES не мешают,
  GES их просто не рендерит.
- **`content/` как git submodule внутреннего репозитория.** Отклонено: ломает обычный клон
  публичным пользователям marketplace (submodule указывает на приватный внутренний хост, не
  резолвится без доступа) и красит `check.sh --fast` у контрибьютора без доступа к внутреннему
  GitLab.
- **Ветки `private`/`public` в одном репозитории (паттерн `nsmp-plugin`).** Отклонено: этот
  репозиторий публичный с первого дня — курировать приватный/публичный срез не от чего, у
  `nsmp-plugin` ветки решают другую задачу (постепенное открытие ранее приватного содержимого).

## Consequences

**Положительные:**
- GitHub остаётся единственным источником правды и единственным местом редактирования — новый
  таргет не создаёт второй копии, за которой нужно отдельно следить на предмет расхождений в
  содержании.
- GES получает каталог без дублирования контента и без изменения структуры репозитория —
  `content/` не переезжает, .doc-root.yaml контракт (ADR-0012) не затронут.
- Механизм воспроизводим для будущих внутренних read-only витрин при необходимости (описанный
  выше multi-push вариант — задокументированная, осознанно не выбранная сейчас опция).

**Отрицательные / trade-offs:**
- Ручной `git push internal main` — нет автоматизации; витрина обновляется, только если кто-то
  не забыл выполнить команду после значимого коммита.
- Витрина может отставать от `origin` произвольное время. Явно принято как допустимое состояние
  (см. таблицу интеграционной точки), но мониторинга самого факта рассинхрона нет.
- Инвариант «`.doc-root.yaml` в `content/`» теперь несёт двойную нагрузку: держит и nauta-контракт
  (`check.sh --fast`), и физическую способность GES отрендерить витрину. Будущий рефакторинг,
  ориентирующийся только на первую нагрузку, рискует не заметить вторую.
- Регистрация в GES (`repositories/tools-ai/gramax-plugin.yaml` + запись в `workspace.yaml`) —
  внешняя зависимость вне этого репозитория и вне этого ADR: до её выполнения PR-ом в
  `nau-gramax-manager` внутренний remote синхронизирован, но нигде не отрендерен.

**Mitigations:**
- `tests/gramax/nauta-integration/ac-003-doc-root-contract.sh` уже проверяет расположение
  `content/.doc-root.yaml`; этот ADR документирует, что тест защищает не только nauta-контракт, но
  и способность внутренней публикации рендериться — следующий рефакторинг увидит это здесь, не
  только в комментарии к тесту.
- Явно зафиксированная read-only-политика внутреннего контура (этот ADR) снижает риск, что кто-то
  начнёт редактировать в Gramax UI, не отдавая себе отчёта, что это меняет архитектуру.
