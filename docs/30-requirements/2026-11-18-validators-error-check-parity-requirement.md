# Паритет офлайн-валидаторов плагина с модулем проверки ошибок приложения

**Контур И:** файл целиком уезжает в стор (Фаза 3) — собственной capability у него нет.

## Уезжает в стор (Фаза 3)

Каркас требования (все разделы ниже) целиком уезжает в стор в Фазе 3; собственной capability у документа нет, поэтому пара дрейфа с openspec/ не объявляется.

## JTBD

Когда я готовлю каталог к публикации через офлайн-гейт (pre-commit/CI) и знаю, что модуль
приложения «Проверка на ошибки» ловит дефекты, которые офлайн-валидаторы пропускают, — битые
пути `<plant-uml>`/`<bpmn>`/`<mermaid>`, несуществующие файлы собственных иконок из `.icons/`, —
а собственный валидатор к тому же помечает «неподдерживаемыми» теги из своего же контракта, я
(сопровождающий плагина gramax) хочу, чтобы `validate_structure.py` покрывал те же
офлайн-проверяемые категории с той же моделью уровней, чтобы дефекты, находимые приложением
уже после публикации, находились до неё, а расхождения офлайн/онлайн были явными, не
молчаливыми.

## Описание

RES-007 зафиксировал состав модуля «Проверка на ошибки» приложения: шесть категорий — статьи,
ссылки, элементы, диаграммы, шапки, иконки — и уровни «Ошибка/Предупреждение» в панели
администрирования; вердикт по плагину — «частично»: проверка иконок `.icons/` и диаграмм — нет
(RES-007 §2). Это требование раскладывает вердикт на офлайн-проверяемые дельты и расширяет
существующий контракт валидации
[Валидация Gramax-каталога как публичный контракт плагина](2026-08-11-validation-contract)
(ADR-0012 [Каталог: контракт валидации](../00-project/adr/0012-catalog-validation-contract),
ADR-0019 [Рендер-киллеры](../00-project/adr/0019-render-killer-linter), ADR-0020
[Рекурсивное обнаружение doc-root](../00-project/adr/0020-doc-root-recursive-discovery)), не
меняя его рамки: офлайн-скрипт, машиночитаемые контракты как единственный источник правды,
warning по умолчанию с объявленным ужесточением.

Дельта доказуемая — две категории. Диаграммы: проверка существования цели покрывает только
`<drawio path>` (W031); `<plant-uml path>`, `<bpmn path>`, `<mermaid path>` парсером ресурсов
не извлекаются вовсе, и битый путь в них проходит офлайн-гейт незамеченным (факты 2–4).
Иконки: проверки нет ни в каком виде — коды `<icon code="..."/>` не резолвятся против
`.icons/<code>.svg`, о котором документация синтаксиса прямо говорит как о проверке модуля
(RES-007 §2, §3); в коде плагина упоминаний `.icons` ноль (факт 6). Попутно вскрыт дефект
согласованности: W034 «неподдерживаемая разметка» срабатывает на канонические теги из
`selfClosingTags` контракта `gramax-tags.json` — `<view>`, `<mermaid>`, `<snippet>`,
`<openapi>`, `<video>`, `<icon>` (факт 7) — а теги с дефисом (`<plant-uml>`) невидимы для
W034 из-за формы паттерна (факт 8). Категории «статьи» и «ссылки»
офлайн уже покрыты; для «шапок» дельта из доступных источников не устанавливается — состав
правил модуля RES-007 не раскрывает; проверку по догадке требование не вводит (вопрос 5).

Факты кода и пробы (2026-11-18):

1. RES-007 §2, строка «Каталог → Проверка на ошибки»: модуль проверяет «статьи, ссылки,
   элементы, диаграммы, шапки, иконки»; уровни «Ошибка/Предупреждение» — в панели админ.
2. `check_diagrams` (`plugins/gramax/scripts/validate_structure.py:719-735`) проверяет только
   `target_type == "drawio"` (W031, warning).
3. Парсер ресурсов знает три типа цели — `"link" | "image" | "drawio"`
   (`plugins/gramax/scripts/lib/md_link_parser.py:26`); `<plant-uml path>`, `<bpmn path>`,
   `<mermaid path>` не извлекаются — паттерна, кроме `_DRAWIO_RE` (`:16`), нет.
4. Проба 2026-11-18: фикстура с битыми целями всех четырёх тегов (`./missing.mmd`,
   `./missing.puml`, `./missing.bpmn`, `./missing.drawio`) — ровно одна находка (W031 по
   drawio); по `<mermaid>`/`<plant-uml>`/`<bpmn>` — ноль.
5. Страница синтаксиса (RES-007 §3): `<plant-uml path>` и `<bpmn>` (`.bpmn`, Camunda XML,
   только файлом) — исходный формат; собственные иконки — `.icons/<code>.svg` рядом с
   `.doc-root.yaml`, проверка иконок — в `catalog/error-check`.
6. Плагин: `writer/SKILL.md:290` — `<icon code="lucide-name"/>`; `doc-root-schema.md:29` —
   `icon:` в свойствах только Lucide; упоминаний `.icons` в `plugins/gramax/` нет.
7. Проба 2026-11-18: `<icon>`, `<view>`, `<mermaid path>`, `<bpmn>`, `<openapi>`, `<snippet>`,
   `<video>` — каждый даёт W034 «неподдерживаемая разметка», при этом все шесть объявлены в
   `selfClosingTags` контракта `gramax-tags.json`; находки живые на `docs/` репозитория —
   `<view>` и `<mermaid>` в `docs/30-requirements/2026-08-11-mermaid-file-based-adoption.md`
   и `docs/10-domain/research/2026-08-11-index-md-at-catalog-root.md` (POINTER).
8. `_UNSUPPORTED_HTML_RE` (`validate_structure.py:744`) — паттерн `[a-z][a-z0-9]*` не совпадает
   с именами через дефис: `<plant-uml ...>` невидим даже для W034 (подтверждено пробой, факт 4).
9. ADR-0012 Решение 2 фиксирует градуировку строгости по природе дефекта (плейсхолдер/битая
   ссылка — error безусловно; сирота — warning); W031 (warning) — ближайший прецедент.

## Scope

### In scope

- Существование файла-цели для `<mermaid path>`, `<plant-uml path>`, `<bpmn path>` — в той же
  семантике, что действующая проверка drawio (W031).
- Резолв кастомных (без префикса `lucide-`) кодов `<icon code="..."/>` против
  `.icons/<code>.svg` catalog root'а.
- Паритет W034 с контрактом тегов: канонические теги не репортятся «неподдерживаемыми»;
  дефисные имена вне контрактов — репортятся наравне с простыми.
- Одна находка на дефект для новых проверок (наследование BR-004 ADR-0012/ADR-0019).

### Out of scope

- Серверные проверки модуля: панель администрирования, уровни в панели, метрики, данные
  пользователей, стайлгайд (LanguageTool XML + LLM, RES-007 §3). Причина: валидатор —
  локальный офлайн-скрипт без сети и без обращений к модели (NFR-004 требования
  [2026-08-11-validation-contract](2026-08-11-validation-contract)); серверное состояние ему
  недоступно по определению границы «плагин/сервер», не по недосмотру.
- Категория «шапки»: состав правил модуля RES-007 не раскрывает (категория названа без
  перечня правил). Проверка по догадке нарушает красную линию «no invented metrics»; сперва —
  исследовательская задача на детализацию `catalog/error-check` (открытый вопрос 5).
- Inline-блоки ` ```mermaid `/` ```plant-uml `: цели-файла нет, офлайн-семантика проверки не
  установлена; их миграция на file-based — зона навыка mermaid (RES-007 §4), не валидатора.
- Полная офлайн-валидация lucide-кодов: требует поставки реестра иконок — техническое
  решение SA (открытый вопрос 1); здесь lucide-коды проверяются только по форме префикса.
- `properties.icon` в frontmatter и `.doc-root.yaml`: документирован как Lucide
  (`doc-root-schema.md:29`); поддержка кастомных кодов движком не установлена (вопрос 2).
- Валидность содержимого диаграмм (синтаксис mermaid, Camunda XML) и рендер (`DIAGRAM_RENDERER_SERVICE_URL`,
  RES-007) — серверный сервис, вне офлайн-инструмента.

## Функциональные требования

### A. Цели диаграммных тегов

- **FR-151:** офлайн-валидатор обязан проверять существование файла-цели для тегов
  `<mermaid path="..."/>`, `<plant-uml path="..."/>`, `<bpmn path="..."/>` — в той же
  семантике, что действующая проверка `<drawio path>` (W031): путь резолвится относительно
  статьи; цель вне границ catalog root (cross-каталожная, граница FR-047/FR-120) не
  резолвится и находки не даёт; отсутствующий файл — находка.
- **FR-152:** битая цель диаграммного тега даёт ровно одну находку на дефект — без
  дублирования от проверки неподдерживаемой разметки по тому же тегу (наследование BR-004,
  демаркация по образцу `validate_structure.py:738-742`).

### B. Собственные иконки `.icons/`

- **FR-153:** для `<icon code="X"/>`, где код `X` не начинается с `lucide-`, валидатор обязан
  проверять существование файла `.icons/X.svg` рядом с `.doc-root.yaml` того же catalog root'а
  (RES-007 §3: `.icons/<code>.svg`); файл отсутствует — находка, называющая код и ожидаемый
  путь. Код с префиксом `lucide-` против `.icons/` не резолвится.
- **FR-154:** проверка иконок ограничена кодами из `<icon code="..."/>` в статьях;
  `properties.icon` (frontmatter статьи, `.doc-root.yaml`) — вне периметра до разрешения
  открытого вопроса 2.
- **FR-155:** отсутствие папки `.icons/` в каталоге само по себе не является дефектом:
  проверка молчит, если ни одной статьи с кастомным кодом иконки в каталоге нет.

### C. Паритет «элементов»: W034 и контракт тегов

- **FR-156:** тег, объявленный в машиночитаемом контракте плагина (`gramax-tags.json`:
  `pairedTags`, `selfClosingTags`), не может получать находку «неподдерживаемая разметка»
  (W034); W034 репортит только теги вне обоих контрактов. Устраняет живые ложные находки
  факта 7. Набор известных тегов вычисляется из контрактов, не литералом в коде (прецедент
  вычисления `known_tags` — `validate_structure.py:741-742`).
- **FR-157:** имена тегов с дефисом (`plant-uml`-форма) подпадают под проверку неподдерживаемой
  разметки наравне с простыми — слепая зона паттерна `[a-z][a-z0-9]*` (факт 8) закрыта; теги,
  объявленные в контрактах, по-прежнему исключены (FR-156).

## Нефункциональные требования

- **NFR-065 (офлайн):** новые проверки — без сетевых обращений и без вызовов модели
  (наследует NFR-004 [контракта 2026-08-11](2026-08-11-validation-contract)). Следствие:
  полная валидация lucide-кодов без поставленного реестра невозможна — см. Out of scope.
- **NFR-066 (обратная совместимость):** новые проверки не покрасят CI живых потребителей
  молча: уровень по умолчанию — warning (прецедент W031, факт 9); ужесточение до error —
  только объявленным breaking change (наследует NFR-001 контракта 2026-08-11). Финальная
  градуировка строгости — решение ADR.
- **NFR-067 (одна находка на дефект):** продолжение BR-004 ADR-0012/ADR-0019 на новые
  проверки (FR-152); дубликатов «W034 + проверка цели» по одному тегу нет.
- **NFR-068 (синхрон контрактов):** добавление `plant-uml`/`bpmn` в контракт тегов — тем же
  коммитом, что код, распознающий теги (прецедент FR-039 контракта 2026-08-11); демаркация
  W034 обновляется из контракта, правкой одной записи JSON.
- **NFR-069 (токен-бюджет):** N/A — проверки исполняются офлайн-скриптом, через LLM не
  проходят.

## User Journey

1. Автор пишет `<bpmn path="./process.bpmn"/>`, файл не создал → офлайн-гейт на коммите
   называет отсутствующую цель (FR-151) — раньше это находил только модуль приложения.
2. Автор вставляет `<icon code="logo-2024"/>` без `.icons/logo-2024.svg` → валидатор называет
   код и ожидаемый путь (FR-153) — до публикации, не в панели админ.
3. Автор использует канонический `<view defs="..."/>` → валидатор молчит: тег объявлен в
   контракте (FR-156); ложные W034 исчезают и на собственном `docs/` репозитория (AC-162).
4. Каталог без `.icons/` и без кастомных иконок проходит без новых находок (FR-155).

Альтернативный путь: каталог с серверными дефектами (метрики, стайлгайд, доступы) —
офлайн-валидатор их не видит и не обязан видеть: граница — Scope → Out of scope явно.

## Бизнес-правила

- **BR-028:** канонический по контракту плагина тег не может быть объявлен собственным
  валидатором «неподдерживаемым» — расширение BR-001 контракта 2026-08-11 на пару
  «контракт тегов ↔ W034» (FR-156).
- **BR-012:** семантика «цель диаграммы существует» едина для всех диаграммных тегов
  (сегодня — четыре: drawio, mermaid, plant-uml, bpmn); новый диаграммный тег = расширение
  той же проверки и строки в контракте, не отдельный механизм (FR-151, NFR-068).
- **BR-013:** кастомный код иконки резолвится против `.icons/` своего catalog root'а;
  `lucide-`-код — против библиотеки иконок, офлайн — только по форме префикса (FR-153).
  Superseded в части с 4.10.0 (ADR-0026 Решение 3): офлайн-валидатор сверяет код с реестром
  `gramax-lucide-icons.json`; формы с префиксом `lucide-` движок не знает.
- **BR-014:** новые проверки — warning по умолчанию; переход к error — объявленный breaking
  change с миграционным окном, не молчаливое ужесточение (NFR-066).

  `uv run plugins/gramax/scripts/validate_structure.py docs | grep -E 'W034: .*<(view|mermaid|snippet|openapi|video|icon)>'` — пусто.

## Инварианты и Safeguards

**Содержательные:**
- Канонический по контракту тег никогда не репортится «неподдерживаемым» (BR-028, FR-156).
- Семантика диаграммной проверки одна на все диаграммные теги; параллельных механизмов нет
  (BR-012).
- Кастомный код иконки резолвится только внутри своего catalog root'а; граница
  cross-каталожных целей (FR-047/FR-120) наследуется, не изобретается заново.
- Одна находка на дефект для всех новых проверок (FR-152, NFR-067).
- Новые проверки офлайн: без сети, без модели, без публикации содержимого каталога вовне
  (NFR-065, наследует NFR-005 контракта 2026-08-11).

**Sensitive content:** N/A — расширение офлайн-валидатора структуры; новых источников PII,
секретов, NDA-контента не вводит; резолв `.icons/` и диаграммных целей — файловые проверки,
как существующие W030/W031.

**Жизненный цикл:** ревизия — при следующем изменении состава диаграммных тегов или иконок в
контрактах плагина проверить, что демаркация W034 и диаграммная проверка обновились из
контрактов, а не литералом в коде (NFR-068), и что категория «шапки» получила детализацию
правил, если модуль приложения её раскрыл. Owner — сопровождающий репозитория (PM).

## Открытые вопросы

1. **Полная офлайн-валидация lucide-кодов** — требует реестра иконок в поставке плагина
   (объём, источник, синхронизация). Решение SA; до него — только форма префикса (FR-153).
2. **Кастомные коды в `properties.icon`** — RES-007 документирует поле как Lucide
   (`doc-root-schema.md:29`); поддерживает ли движок там `.icons/`-коды — не установлено.
   Задача PM; положительный ответ расширяет FR-153 на свойства.
3. **Коды новых находок** — наследуют W031 или получают собственные коды: потребители грепают
   коды в CI, смена контракта вывода заметна им (ср. W032/W033/W034). Решение SA.
4. **Форма `icon:<код>` в ключах `logo`/`logo_dark`** `.doc-root.yaml` (RES-007 §2) —
   резолвится ли против `.icons/` — не установлено; кандидат на объединение с вопросом 2.
5. **Категория «шапки»** — состав правил модуля не документирован в RES-007 (названа без
   перечня). Нужен второй проход исследования по `catalog/error-check`; до него
   офлайн-проверки по этой категории не вводятся (красная линия «no invented metrics»).
6. **Градуировка строгости новых проверок** — warning по умолчанию (NFR-066, прецедент W031)
   или error по природе дефекта (образец Решения 2 ADR-0012) — закрепится в ADR; решение SA.
