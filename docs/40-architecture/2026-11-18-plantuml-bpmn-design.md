# PlantUML/BPMN-авторство — навык plantuml: плейсмент, контракт тегов по движку, границы, тест-хуки

**Опоры:** `docs/30-requirements/2026-11-18-plantuml-bpmn-requirement.md`,
`docs/00-project/adr/0023-plantuml-bpmn-skill.md`,
`plugins/gramax/skills/plantuml/SKILL.md`

## Контекст

Реализация требования [Авторство PlantUML/BPMN-диаграмм в Gramax (file-based, без
конвертационных пайплайнов)](../30-requirements/2026-11-18-plantuml-bpmn-requirement.md)
(FR-141…FR-148, NFR-059…NFR-064, AC-051…AC-062, BR-008…BR-011). Факт-база —
[RES-007](../10-domain/research/2026-11-18-enterprise-server-skill-gap.md) (§2 строка
«Статья → Диаграммы» — вердикт «частично»; §3—§4 — теги `<plant-uml path>`/`<bpmn path>`,
inline-блоки, `DIAGRAM_RENDERER_SERVICE_URL`) — и ground truth движка — blobless-клон
`github.com/Gram-ax/gramax` на пине `48592b36` (то же окно, что RES-006/RES-008), прочитанный
напрямую при подготовке этого дизайна; метод «движок = первичный источник поверх docs» —
[RES-008](../10-domain/research/2026-11-18-writer-docs-divergence-audit.md) (аудит параллельного
потока, in-flight — цитируется как метод-прецедент, не как единственная опора).

Факты движка, на которых стоят решения ниже (все `путь:строка` — относительно корня движка
на пине `48592b36`; чтение кода, исполнение не запускалось — та же оговорка об уверенности,
что у RES-008 §7):

| Факт | Evidence |
|---|---|
| Тег `plant-uml` зарегистрирован в реестре контентных тегов | `core/extensions/markdown/core/render/logic/getRenderElements/getTagElementRenderModels.ts:57` |
| Схема атрибутов `plant-uml` (общая с `mermaid` через `getMarkdocModel`): `path`, `title`, `width`, `height`, `float`, `scale` — все String; `path` регистрируется в ResourceManager как ресурс статьи | `core/extensions/markdown/elements/diagrams/getters/markdocModel.ts:16-33`; `core/extensions/markdown/elements/diagrams/logic/getAttrs.ts` |
| Рендер PlantUML — только серверный: `POST {DIAGRAM_RENDERER_SERVICE_URL}/convert/plantuml`; без URL рендер-сервиса движок выдаёт ошибку `no-diagram-renderer` | `core/extensions/markdown/elements/diagrams/diagrams/plantUml/getPlantUmlDiagram.ts`; `requestPlantUmlDiagram.ts`; `core/logic/components/Diagram/Diagrams.ts` |
| Enum типов диаграмм — только `Mermaid` и `Plant-uml` | `core/logic/components/Diagram/DiagramType.ts` |
| **Тега/типа `bpmn` в движке на пине нет вовсе**: 0 совпадений `grep -rni bpmn` по всему дереву (без node_modules); в реестре тегов и enum типов отсутствует | поиск по дереву на пине; реестр `getTagElementRenderModels.ts:56-63` |
| Salt-обработки в движке нет — Salt это PlantUML-контент через тот же `/convert/plantuml`; поддержка зависит от конфигурации рендер-сервиса (внешний по отношению к репозиторию движка) | 0 совпадений `salt` по `core/`; единственный путь рендера — `Diagrams.ts` |

Расхождение «docs документируют `<bpmn path>`, движок на пине его не знает» — тот же класс,
что `<gallery>` в RES-008 §5 (docs опережают пин окна движка). Обрабатывается политикой
verify-before-include (раздел «Контракт тегов»), не молчаливым включением и не стоп-правилом
BR-008 (его предмет — конвертационные pipeline'ы, которых здесь нет и не будет).

Плейсмент меняет публичную поверхность плагина (новый скилл, semver, правка публичного
`marketplace.json`-описания, триггерные границы с `gramax:mermaid` и `gramax:drawio`) —
зафиксирован в [ADR-0023](../00-project/adr/0023-plantuml-bpmn-skill.md). Настоящий документ
несёт то, что ADR намеренно не несёт: план файлов, контракт тегов и триггеров, маппинг
FR/NFR, стоп-правило и тест-хуки для QA-author.

## Контракт тегов (Q-4)

### `<plant-uml>` — по схеме движка на пине

Схема `getMarkdocModel` (общая для `mermaid`/`plant-uml`,
`core/extensions/markdown/elements/diagrams/getters/markdocModel.ts:16-33`):

| Атрибут | Тип | Назначение | В каноническом выводе навыка |
|---|---|---|---|
| `path` | String | ссылка на `.puml`-файл; файл регистрируется как ресурс статьи (`ResourceManager.set`) | всегда — единственный обязательный на практике атрибут (без него `src` пуст, движок даст `cannot-get-data`) |
| `title` | String | подпись | только по явному запросу |
| `width` | String | ширина | только по явному запросу, значение со спецификатором (напр. `800px`) |
| `height` | String | высота | только по явному запросу (напр. `450px`) |
| `float` | String | обтекание | только по явному запросу |
| `scale` | String | масштаб; `getAttrs` принимает форму с `px` и без (число) | только по явному запросу; семантика числовой формы для диаграмм движком не документирована и здесь не утверждается |

Канонический вывод навыка — минимальная самозакрывающаяся форма с пустой строкой до и
после (FR-144, прецедент mermaid/ADR-0010):

```markdown
<plant-uml path="./overview-auth-flow.puml"/>
```

**Дефолты размеров не изобретаются.** Прецедент mermaid (`width="800px" height="450px"`)
опирался на ground truth `blocks.md` writer'а; для plant-uml writer не содержит ни одного
упоминания (RES-007 §2, проверка 2026-11-18) — значение «пустое поле лучше правдоподобного»:
навык не подставляет размеры, пока пользователь не попросил.

### `<bpmn>` — контракт docs, в движке на пине отсутствует

- Задокументированная форма (RES-007 §3): только файловая — `.bpmn` (Camunda XML) + тег
  `<bpmn path="./<имя>.bpmn"/>`; inline-формы для bpmn в docs нет и не выдумывается (FR-143).
- Ground truth движка на пине `48592b36`: тег `bpmn` не зарегистрирован (реестр тегов, enum
  `DiagramType`), 0 совпадений по дереву. Docs (живой сайт, ноябрь 2026) опережают пин окна
  движка (jul—sep 2026) — противоречие того же класса, что `<gallery>` (RES-008 §5).
- **Политика verify-before-include:** навык авторит `.bpmn` + тег по документированной форме
  (авторство — корректно относительно docs; рендер — ответственность движка, BR-009), но
  публичные обещания (description, CHANGELOG) формулируются как «авторство по документации
  движка; рендер тега `<bpmn>` на проверенном окне движка не подтверждён — проверь в своём
  окружении». Перед релизом — однократный runtime-probe в живом окружении (см. «Открытые
  вопросы»): минимальный `.bpmn` + тег в scratch-каталоге, открытие в реальном Gramax.
  - Probe прошёл → оговорка снимается, обещание рендера — по факту.
  - Probe не прошёл → эскалация PM: либо BPMN остаётся в навыке с постоянной оговоркой
    (движок догонит docs), либо дескоп FR-143 ревизией требования. **Никакого локального
    рендера/конвертации не строится ни в каком исходе** (BR-008).

## Контракт триггеров (description и fallback)

### description нового навыка (целевой текст для Dev; финальная редакция — Dev, формулировки AC обязаны матчиться)

```yaml
name: plantuml
description: "Только для PlantUML- и BPMN-диаграмм — НЕ для mermaid и drawio. Создание PlantUML-исходников (включая Salt-макеты интерфейсов) и BPMN-процессов (Camunda XML) для документации Gramax: пишет исходник в .puml/.bpmn-файл рядом со статьёй и вставляет тег-ссылку в md. Используй когда: «нарисуй plantuml / plant-uml / puml», «UML-диаграмма» (компоненты, развертывание, активности, таймлайны), «Salt», «макет интерфейса», «bpmn», «BPMN-процесс», «Camunda». Рендер — движок Gramax (серверный рендер диаграмм). Без внешних зависимостей, без скриптов, без preview. Не для: mermaid DSL → gramax:mermaid; drawio / .drawio → gramax:drawio."
```

Свойства: позитивные ключи — ровно список FR-146; негативная демаркация — по паттерну пары
mermaid/drawio (ADR-0009 Решение 5); generic-триггеры («нарисуй диаграмму» без движка) навык
**не** ловит — владельцем остаётся `gramax:mermaid` (ADR-0009 Решение 1, не пересматривается).

### Расширение fallback-диалога mermaid (FR-146, эволюция ADR-0009; BR-011 — только формулировки)

Целевой текст секции «Fallback при ambiguous-request» в `mermaid/SKILL.md` (заменяет текущий
диалог из двух опций; слова «plantuml», «bpmn», `<plant-uml path>` допустимы, литералы
`@startuml` и `.bpmn` — **запрещены** в этом файле целиком, их ловит AC-059):

> Какой движок использовать для диаграммы?
>
> 1. **mermaid** — файл `.mermaid` рядом со статьёй, тег-ссылка в md; рендер
>    Gramax-фронтендом. Подходит для flowchart, sequence, gantt, ER, state, class, pie,
>    mindmap.
> 2. **plantuml** — файл `.puml` рядом со статьёй, тег `<plant-uml path>` в md; UML-семантика
>    (компоненты, развертывание, активности, таймлайны), Salt-макеты интерфейсов →
>    `gramax:plantuml`.
> 3. **bpmn** — бизнес-процесс в нотации BPMN (Camunda XML), файл + тег `<bpmn path>` →
>    `gramax:plantuml`.
> 4. **drawio** — через внешний плагин `Agents365-ai/drawio-skill`; создаёт `.svg`-файл рядом
>    со страницей. Подходит для сложных схем, кастомных стилей.
>
> По умолчанию — **mermaid**, если не укажешь.

Решение о дефолте (Q-1, часть): **mermaid остаётся дефолтом неявного запроса** — смена
дефолта была бы несовместимым изменением публичного поведения `gramax:mermaid` (major по
ADR-0006) и нарушала бы BR-011; желание Story 4 закрыто присутствием plantuml/bpmn в списке
вариантов, не сменой дефолта.

Симметрично: из fallback-строки drawio в `mermaid/SKILL.md` (опция 2 текущего текста:
«Подходит для сложных схем, BPMN, кастомных стилей») и из `drawio/SKILL.md` (та же формула
в его собственном fallback) «BPMN» убирается — теперь это опция 3 с владельцем
`gramax:plantuml`. Description'ы mermaid и drawio получают по одному анти-триггеру
«Не для PlantUML/BPMN → gramax:plantuml».

### Граница с внешним drawio-skill

Не меняется: drawio — делегация внешнему плагину (ADR-0008/0009). Единственная правка —
перенос BPMN из «подходит»-списка drawio в отдельную опцию (выше). Anti-trigger «drawio /
.drawio → gramax:drawio» в description plantuml удерживает обратную границу.

## Политика inline-формы (Q-2)

**Решение — вариант (i): file-based канон, inline распознаётся с предложением миграции.**

- Единый канон авторства DSL-диаграмм во всём плагине: `.puml`-файл + тег-ссылка, как
  `.mermaid` в ADR-0010. Одна конвенция именования на все текстовые диаграммные форматы
  (FR-147 явно запрещает вторую параллельную конвенцию); защита от перезаписи и идемпотентность
  (FR-148, NFR-061) определены только для файловой формы.
- То, что docs документируют inline ```plant-uml как текущую форму, канону не противоречит:
  движок поддерживает обе формы, плагин выбирает стандарт авторства — та же ситуация, что у
  mermaid (docs документируют inline, плагин с v4.0.0 канонизирует file-based).
- **Поведение при чтении `target_page`** (FR-145): обнаружен fenced-блок
  ```` ```plant-uml ```` (в т.ч. с опциями `{title, scale, float}`) → уведомление
  «inline-форма распознана; канон плагина — файл + тег-ссылка» + предложение точечной
  миграции: извлечь исходник в `<page-slug>-existing.puml`, заменить блок на
  `<plant-uml path="./<имя>.puml"/>`; опции блока переносятся в атрибуты тега 1:1
  (`title→title`, `scale→scale`, `float→float` — обосновано схемой движка, см. Q-4).
  **Без явного подтверждения файл не трогается** (BR-010, принцип ADR-0010 Решение 3).
- Batch-миграция inline-блоков по каталогу — вне scope (требование, Out of scope); если
  появится запрос — отдельная задача по прецеденту
  [mermaid-migration](../30-requirements/2026-08-11-mermaid-file-based-adoption.md) (FR-054—FR-060)
  и `scripts/migrate_mermaid.py`.

## Инстанцирование конвенции именования (FR-147)

Правила дословно наследуются от mermaid (ADR-0010 Решение 2), меняются только расширения —
второй конвенции не вводится:

- `<page-slug>` — имя `target_page` без расширения; `_index.md` → имя родительской директории.
- `<diagram-slug>` — тематическое имя из запроса; kebab-case, ASCII, ≤ 30 символов
  (обрезка по целым словам); fallback `diagram`; кириллица → два варианта на выбор
  (семантический перевод на английский / ввод пользователем), без автотранслитерации
  (прецедент ADR-0010 Решение 2); запрещённые символы `: * ? " < > | \` и пробелы → `-`.
- Итог: `<page-slug>-<diagram-slug>.puml` / `<page-slug>-<diagram-slug>.bpmn`; файл — в той
  же директории, что `target_page` (не в assets-папке).
- Коллизия (FR-148): прочитать первые 5 строк существующего файла, показать, предложить
  перезаписать / другое имя / отмена; без явного «перезаписать» файл не трогается
  (NFR-061, ADR-0010 Решение 2).

Примеры для Dev (по прецеденту mermaid): `docs/auth/overview.md` + «диаграмма компонентов» →
`overview-component-diagram.puml`; `docs/process/_index.md` + «процесс заказа» →
`process-order-flow.bpmn`; тема не названа → `overview-diagram.puml`.

## Окружение рендера и Salt (Q-5)

- **Salt остаётся в scope авторства** (FR-142): `@startsalt`/`@endsalt` пишутся в тот же
  `.puml`-файл, вставка — штатным тегом `<plant-uml path="…"/>`, отдельного механизма нет.
- Оговорка окружения шире Salt: **весь** PlantUML-рендер в движке серверный
  (`POST {DIAGRAM_RENDERER_SERVICE_URL}/convert/plantuml`); без рендер-сервиса (например,
  локальная OSS-конфигурация без переменной) движок выдаёт `no-diagram-renderer`. Навык
  авторит исходники в любом окружении, но несёт одну строку: «рендер PlantUML/Salt требует
  настроенного рендера диаграмм движка (облако/GES); в окружении без него диаграмма не
  отобразится — это свойство окружения, не дефект авторства».
- Поддерживает ли рендер-сервис Salt (`@startsalt`) конкретной конфигурации — из этого
  репозитория **не измеримо** (сервис внешний по отношению к движку; N/A — нет данных);
  закрывается тем же релизным runtime-probe, что и `<bpmn>` (см. «Контракт тегов» и
  «Открытые вопросы»). Salt из scope не снимается (позиция требования Q-5).

  ADR-0006); правка публичного `marketplace.json` санкционирована ADR-0023.

## Стоп-правило BR-008 — нет конвертационных пайплайнов

Зафиксировано в трёх точках носителя:

1. **Секция «Стоп-правило» в `plantuml/SKILL.md`** (обязательная, как «Граница исполнения»
   у export): «Навык никогда не конвертирует `.puml`/`.bpmn` в SVG/PNG и не вызывает
   локальных рендеров (PlantUML/Java, npm, draw.io desktop). Если формату понадобился
   локальный рендер/конвертация для отображения — это стоп: эскалация пользователю к SA/PM,
   не строительство pipeline (анти-ADR-0008)».
2. **BR-009 синхронно:** единственные артефакты навыка — исходник и тег-ссылка в статье;
   производных файлов не создаётся.
3. **Частный случай уже сработал на дизайне**: отсутствие `<bpmn>` в движке на пине
   обработано verify-before-include + эскалацией PM (раздел «Контракт тегов»), а не
   каким-либо локальным компенсатором — прецедент применения стоп-правила без нарушения
   скоупа требования.

**Edge cases / boundary conditions:**

- `target_page = _index.md` → `page-slug` из родительской директории (отдельно от стандартного кейса).
- Тема по-русски → навык предлагает семантический перевод и ручной ввод, автотранслитерации нет.

## Открытые вопросы

1. **Релизный номер** — развод с export-волной (оба заявили additive minor; ADR-0022 назвал
   4.7.0): один общий минор или два последовательных — решает PM по прецеденту ADR-0018.
2. **Runtime-probe `<bpmn>` и Salt** — исполняется PM/qa-runner в живом окружении (облако или
   GES с настроенным `DIAGRAM_RENDERER_SERVICE_URL`) до релизного обещания рендера; исход
   «не прошёл» → решение PM (оговорка-навсегда vs дескоп FR-143), конвертационный pipeline
   исключён в любом исходе (BR-008).
3. Замеченные при аудите движка теги `db-diagram`/`db-table` (реестр тегов, пин) — вне этого
   требования; кандидат в будущие разведки, здесь фиксируется только как факт.
