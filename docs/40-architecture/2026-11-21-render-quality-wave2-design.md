## Контекст

Исполнительская расшифровка требования [Волна-2 калибровки render-quality](../30-requirements/2026-11-21-render-quality-wave2-requirements.md)
(FR-199…FR-207, AC-120…AC-128, NFR-083; BR-021…BR-024 волны-1 действуют без изменений — D8).
Решения владельца D1–D8 волны-2 закреплены в
[дереве волны-2](../00-project/epics/2026-11-21-render-quality-wave2-genesis-tree.md) и не
переобсуждаются; решения волны-1 наследуются финально. Фактическая база —
[запись замера волны-1](../60-implementation/acceptance/2026-11-21-render-calibration-validate-render.md):
th отдал 200 на этой цели (дрейф рендерера), деградационные симптомы
`unbalanced-pair-tags`/`multiple-images` tier-0 не судит, живая форма
`pageUrlTemplate` получена от владельца.

Нового архитектурного контура волна не строит — прибор волны-1 (ADR-0025, Решения 1–8
дизайна волны-1) остаётся каркасом. Документ несёт четыре SA-шва волны-2: живая форма
конфига (FR-205), жизненный цикл пробных страниц (FR-203/204), контракт tier-1 на живой
цели (FR-206), механика судьбы th-вердикта одним циклом (FR-199…FR-202).

## Решение 1 — конфиг живой цели: живая форма pageUrlTemplate (FR-205, AC-126)

### Поля и форма

Конфиг `scripts/render-quality/render-target.local.json` (вне git, `.gitignore:30`) несёт
постоянные поля `baseUrl`, `token`, `catalog`, `pageUrlTemplate` живой формы
`{base}/{каталог}/{путь-страницы}` — **без сегмента `/page/`**, в отличие от примера схемы
волны-1 (факт 5). Живая форма — данные владельца (D3), зафиксированные в сессии; прибор
форму не изобретает. Живой пример-страница владельца воплощён в конфиге самой живой формой
шаблона — отдельного поля для него схема не заводит: **схема конфига не расширяется**
(факт 5, non-goals требования).

Пример схемы `scripts/render-quality/render-target.example.json` переводится на живую
форму — единственное изменение значения:

```json
"pageUrlTemplate": "{base}/{catalog}/{slug}"
```

Хост-заполнитель `https://render-target.example.invalid` (RFC 2606) сохраняется — пример
остаётся единственным коммитимым файлом прибора с литералом `https://`. Синхронную правку
таблицы настройки цели в runbook и карты фикстур README сюиты несёт документарное закрытие
(FR-207б) — команды документов сверены с фактическим прибором.

### Как config.py разрешает и отказывается (именованные отказы)

Код `config.py` **не меняется**: валидатор (Решение 1 волны-1) принимает произвольную
форму шаблона при наличии `{slug}`, и живая форма укладывается в неё. Поведение
фиксируется как контракт волны-2:

| Ситуация | Исход |
|---|---|
| `pageUrlTemplate` отсутствует, в `tiers` есть tier-1/tier-2 | `RENDER_TARGET_INVALID`, поле `pageUrlTemplate`, подсказка называет поле и путь конфига; отказ до любого обращения к playwright (лестница Решения 2 волны-1) |
| `pageUrlTemplate` не строка либо не содержит `{slug}` | тот же код и то же поле — «malformed» и «missing» неразличимы для отказа, подсказка одна |
| `tiers` = только `tier0` | поле опционально, не читается, отказов не даёт |
| страница на цели недостижима | это **не** отказ конфига: именованный факт tier-0 (`NOT_FOUND`/`HTTP_4XX`/`NETWORK_ERR`) + именованный skip tier-1 (Решение 3) |

Новых кодов отказа волна не вводит: `RENDER_TARGET_UNSET`/`RENDER_TARGET_INVALID`/
`PLAYWRIGHT_UNAVAILABLE`/`PLAYWRIGHT_NO_BROWSER` остаются полным набором. «Зелёного без
прогона» нет ни в одном пути волны-2 (альтернативный путь требования).

### Шов подстановки {slug} (открытый вопрос 2 — решение)

Подстановка в `config.py::_substitute` остаётся без изменений: слаг кодируется
`quote(slug, safe="")`, что для плоских слагов фикстур (`[a-z0-9_-]`, FR-187)
тождественно — подстановка не искажает адрес. Живая форма отображается в шаблон
`{base}/{catalog}/{slug}`, где `{slug}` — **последний сегмент пути** (лист): страницы проб
— плоские слаги, пуш кладёт их в корень живого каталога. Составной путь-страницы
(вложенные подкаталоги) волна не вводит: это выбор структуры каталога владельцем, а не
расширение схемы прибора; если он когда-нибудь понадобится, это новая проектная задача на
шве `_substitute`, а не молчаливое расширение. Проверка шаблона остаётся единственной —
«содержит `{slug}`» (усиление до «{slug} — последний сегмент» не вводится, чтобы не
отсекать легальные формы чужих порталов); лист-позиция — операционная норма runbook.

### Где живут живые значения

Хост, слаг живого каталога, живой шаблон и токен — только в gitignore-конфиге и env
(`GRAMAX_RENDER_BASE_URL`, `GRAMAX_RENDER_CATALOG`, `GRAMAX_API_TOKEN` — старшинство
Решения 1 волны-1 без изменений). Токен волны-1 погашен; свежий выпускается к фазе замера
по необходимости (OI-1 дерева волны-2) и живёт в env либо поле `token` вне git (D6,
NFR-081). `render-target.local.json` в этой волне не правится документом — его живые
значения переносит владелец/исполнитель в сессии; проверяемый исход AC-126:
`git check-ignore` подтверждает, `probe.sh --check-env` зелёный, отчёт называет цель.

## Решение 2 — пробные страницы: санкция, именование, уборка (FR-203/FR-204, AC-124/AC-125)

### Именование — структурная необходимость

Имя страницы на цели = имя файла фикстуры без `.md` (плоский нейминг, FR-187). Это не
конвенция по выбору, а структурная необходимость: прибор адресует страницу как
`target.page_url(slug)`, где `slug` — имя файла фикстуры (`probe.py::load_fixtures`);
любой префикс/пространство имён разорвал бы адресацию и дал `NOT_FOUND` по всем строкам.
Префиксов пробных страниц волна не вводит.

### Минимальный состав (открытый вопрос 3 — предложение)

Все пробные страницы — **существующие фикстуры**, нового контента волна не создаёт:

| Нога волны | Страницы (дефект + контроль) |
|---|---|
| Судьба th (FR-199) | `th-in-table` + `control-table` (легальная форма `<td>` + `header="row"` — сторона «нормы») |
| tier-1: несбалансированные теги (FR-206) | `unbalanced-pair-tags` + `control-balanced-tags` |
| tier-1: несколько изображений (FR-206) | `multiple-images` + `control-images` |

Шесть страниц; A/B-твин для th при потребности строгого замера решает исполнитель
(FR-199: «A/B-твин при потребности»), инфраструктура `*-ok` готова записью волны-1.
Окончательный состав фиксирует санкция владельца в сессии (открытый вопрос 3) —
предложение выше есть минимально достаточный набор по фактам волны-1.

### Жизненный цикл одной санкции

Санкция владельца в сессии покрывает **весь** цикл — создание и уборка одним актом
санкции (FR-203: замер без уборки санкцию не закрывает):

1. **Пуш-коммит** выбранных `.md`-фикстур в живой каталог пользовательской документации
   (файлы `.expect.json` на цель не пушатся — данные прибора, прибор читает их из репо).
   Пуш — стандартная git-рутина по разделу «Пуш фикстур на цель» runbook; sync/push-навыки
   не строятся (решение 4 волны-1, D5).
2. **Замеры** по протоколу FR-196/FR-198 (судьба th) и прогон tier-1 (FR-206) —
   `probe.sh` с живым конфигом, отчёт в gitignore-каталоге `results/`.
3. **Уборка** — коммит удаления ровно файлового списка пуш-коммита.

Манифест проб = файловый список пуш-коммита — отдельного реестра сессии не заводится:
коммит и есть записанный факт (Story 2 требования: факты, а не память сессии). Запись
замера называет оба хэша — прецедент волны-1 (пуш `9aef498`, уборка `94e3068`, окно
присутствия ~25 минут). Проверяемость уборки — владельцем на портале: после уборки на
живом каталоге страниц проб нет (AC-124).

### Детерминизм и именованные отказы в цикле

- До пуша `NOT_FOUND` — ожидаемое именованное состояние с нотой (Решение 6 волны-1);
  устойчивый 5xx сразу после пуша — именованный кандидат на переиндексацию, окно числом
  не кодируется (NFR-080), перезапуск после переиндексации — операционная норма (R3 волны-1).
- После уборки живой прогон честно краснеет `NOT_FOUND` по бывшим пробным страницам —
  это D8-поведение прибора, не дефект; замерные прогоны волны идут `probe.sh` напрямую.
- Отчёт детерминирован (NFR-077), лежит в gitignore-каталоге `results/` и в коммиты не
  идёт (прецедент волны-1: `real-target-report.md` вне git); stdout зеркалит отчёт —
  вставка прогона в коммитируемый документ запрещена.

### Гигиена живых значений и толкование грепа AC-125 (названо явно)

В gitignore-конфиге: `baseUrl` (хост), `token`, `catalog` (слаг живого каталога),
`pageUrlTemplate` (живая форма). В публичных файлах — только плейсхолдеры
`{base}`, `{catalog}`, `{slug}` (ADR-0014, files-only; гит-история не переписывается).
Греп AC-125 исполняется двумя ногами с явной семантикой:

- **Слаг живого каталога** — пуст по всему отслеживаемому дереву, кроме одного
  известного исключения: запись замера волны-1 называет слаг временного каталога приёма
  (записана до вступления FR-204). Перезапись принятой записи замера — решение
  владельца/PM, не SA (риск R1); волна-2 собственных упоминаний не создаёт.
- **Имена пробных страниц** — нога применима к страницам, созданным сессией **сверх**
  фикстур (ветка «отдельные пробы» открытого вопроса 3); при дефолтном наборе таких имён
  не возникает — нога N/A с явным названием. Имена дефолтного набора — публичные имена
  фикстур (FR-187): имя файла = имя конструкции, сами фикстуры и буква FR-200 называют
  `th-in-table` в публичных файлах; секретом они быть не могут по построению.

Это толкование делает AC-125 исполнимым и не ослабляет его: две реальные ноги гигиены
(слаг каталога, хост/токен/шаблон) проверяются грепом полностью.

## Решение 3 — tier-1 на живой цели (FR-206, AC-127)

### Адресация и лестница судейства

tier-1 открывает `target.page_url(slug)` — живой шаблон из конфига (FR-205) с
`{slug}` = слаг фикстуры. Судейство идёт по существующей лестнице `probe.py::_probe_row`:
tier-1 судится только при факте tier-0 `OK`; при недоступности — именованная skip-строка
`skip (tier0 <ФАКТ>)`, не тишина. Код `tier1_dom.py` и `probe.py` **не меняется** —
волна-2 укладывается в примитив ассерта волны-1 `{"name", "selector", "count"}`.

### Ассерты — данные, не код

Волна-2 судит деградационные симптомы класса 2 разбора волны-1 (факт 4), которых tier-0
не видит. Ассерты заводятся в `expect.json` как данные (изменяются три файла ожиданий,
код прибора — нет):

| Фикстура | `tier1` | Ассерты (гипотезы R2) | Основание ожидания |
|---|---|---|---|
| `unbalanced-pair-tags` | `pass` | `[{"name": "tail-paragraph", "selector": "text=Абзац после конструкции", "count": 1}]` | волна-1: хвостовой абзац присутствует в HTML — симптом грубой пробой не пойман |
| `multiple-images` | `pass` | `[{"name": "img-count", "selector": "img", "count": 2}]` | волна-1: 2/2 img отрендерились |
| `control-balanced-tags`, `control-images` | `pass` (уже в дереве с волны-1) | селекторы контента контроля | роль: подтверждение селекторов на легальной форме |

Ожидания `tier0` обеих симптом-фикстур **остаются `kill`** (апстрим-строки ERROR-4/ERROR-5,
карта README) — волна не меняет апстрим-гипотезы; на живой цели эти строки дают
tier0-divergence (200 против `kill`) при осмысленной tier1-строке, обе линии отчёта
видны. Запись замера/at-acceptance дополнение извлекает tier1-вердикты — изменение
вердиктов `validate_render` по этим правилам в волну-2 не входит (BR-021; предмет
замера следующего цикла).

### Подтверждение селекторов (R2 — антифабрикация волны-1)

Селекторы в таблице выше — гипотезы до живого замера (README «Антифабрикация»). Первый
живой прогон подтверждает их на контроле (контент заведомо присутствует → `pass` по
построению), затем те же селекторы судят дефект-страницы. Селектор, не сошедшийся на
контроле, — расхождение гипотезы с фактом: разбирается по протоколу FR-196 в записи
замера волны-2, молчаливой правки селектора нет. Ожидание `pass` у симптом-фикстур —
текущий измеренный факт волны-1: если деградация воспроизведётся (ассерт `fail`), это
расхождение → красная строка отчёта → именованный вердикт для следующего цикла.

### Ожидаемая форма отчёта волны-2 (для BA-acceptance)

На живой цели с запушенным минимальным набором: `th-in-table` — `match` после цикла
понижения (`ok` против 200); `control-table`, `control-balanced-tags`,
`control-images` — `match` при подтвердившихся селекторах; `unbalanced-pair-tags`,
`multiple-images` — tier0-divergence (апстрим-гипотеза `kill` против факта 200) с
tier1-вердиктом как предметом записи. Именованные отказы: дефектный/отсутствующий
`pageUrlTemplate` → `RENDER_TARGET_INVALID` до прогона; недостижимая страница →
tier-0-факт + `skip (tier0 …)`; новых кодов отказа нет (Решение 1).

## Решение 4 — судьба th-вердикта одним циклом (FR-199…FR-202, AC-120…AC-123)

### Путь замера

Судьбу th решает **только** повторный замер по протоколу FR-196/FR-198: прогон прибора
(tier-0 факт по `th-in-table`) и прогон валидатора по той же фикстуре — на боевой цели,
по живому конфигу (FR-205). Факт 200 волны-1 сам по себе основанием понижения не
является (FR-199); апстрим-статус «канонический киллер» решением не является (BR-021).
Легальная нога — `control-table`; строгий A/B-твин — по потребности исполнителя.
Валидатор до замера: ERROR ×2 (L8/L9) — факт записи волны-1; свежий прогон фиксирует
стартовое состояние записи.

### Подтверждённый 200 → понижение синхронно в двух носителях

1. **`plugins/gramax/gramax-render-rules.json`**: запись `th` в `killerTags` получает
   атрибут `"severity": "warn"`; сообщение переводится в WARN-семантику — «потенциальный
   киллер апстрима, не подтверждённый на этой цели» (рекомендация, не констатация сбоя
   рендера); подсказка замены (`<td>` + `header="row"`) сохраняется. Точную формулировку
   фиксирует исполнитель в цикле (открытый вопрос 1).
2. **`plugins/gramax/scripts/validate_render.py`**: киллерный проход становится
   severity-aware — записи `killerTags` с `severity=error` (дефолт при отсутствии
   атрибута) дают `E()`, поведение существующих носителей не меняется; `severity=warn`
   даёт `W()`. Поглощение th-баланса (`th_killer_fired`) сохраняется **только** для
   ERROR-киллера: warn баланс th не подавляет — th остаётся в `balanceTags`, и
   несбалансированный `<th>` продолжает давать ERROR баланса. Иначе понижение молча
   ослабило бы существующее правило баланса — дефект адаптации (NFR-083).
3. **rc-контракт валидатора не меняется** (0/1/2, NFR-001): th-WARN не даёт rc=1;
   WARN-строки exit не красят (AC-121).

**Выбор носителя — атрибут `severity`, а не новый список `warnTags`** (назван явно):
`validate_structure.py` строит `known_tags` из `killerTags` (W034-подавление,
ADR-0019 Решение 3 / ADR-0024) — перенос th в новый список молча изменил бы вердикты
отложенного трека и сломал ногу ac-012; атрибут сохраняет membership, и
`validate_structure.py` волной не трогается вовсе (отложенный трек — вне скоупа, D8).

### Подтверждённый отказ → правило остаётся

Если повторный замер фиксирует подтверждённый отказ (ошибка/500 на `th-in-table`),
правок нет ни в одном из двух носителей; запись замера называет отказ основанием
сохранения ERROR (FR-201/AC-122). Отсутствие замера — не основание ни понижения, ни
правки (BR-021).

## Суждение об ADR (названо явно)

**Волна-2 не заводит новых ADR.** Разбор по решениям:

- **Живая форма конфига** — данные прибора в доме Решения 1 волны-1; структурные
  свойства (питон-биндинг, uv, сетевой `--full`) уже несёт ADR-0025. Форма шаблона —
  данные владельца, не структурное свойство контура.
- **Жизненный цикл пробных страниц** — операционная рутина поверх стандартного git;
  автоматизации и новых поверхностей не вводится (sync/push-навыки — никогда) —
  ADR-достойного предмета нет; механика живёт в runbook и здесь.
- **Механика th** — эволюция контрактного файла в доме ADR-0012/ADR-0019/ADR-0024:
  аддитивный атрибут, единственный кодовый потребитель (`validate_render.py`), второй
  читатель (`validate_structure.py`) не меняется. Выбор носителя и его совместимость
  несёт Решение 4 этого документа; тела перечисленных ADR не правятся.
- **Гигиена живых значений** — расширение охвата FR-204 поверх ADR-0014 (files-only,
  история не переписывается) без правки тела ADR-0014.

Ни одно из решений не меняет структурных свойств dev-контура (зависимости, сетевой
шаг, границы контуров) — критерий ADR не достигается ни одним из четырёх швов.
