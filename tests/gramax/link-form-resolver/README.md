# tests/gramax/link-form-resolver/ — контракт инференса расширения `.md`/`_index.md`

Suite тест-дизайна (QA-author, до реализации Dev) для резолвера гейта — трек
`FR-082`/AC-008…012 требования `content/30-requirements/2026-08-13-link-form-contract.md`.
Прецедент структуры — `tests/gramax/catalog-validator/` (ADR-0012 Решение 5): `ac-NNN-*.sh` +
`run.sh` + независимая копия `lib/assert.sh`, читаем `$?`, не grep по stdout как источник
истины об успехе/провале (grep используется только для проверки СОДЕРЖИМОГО сообщения, после
того как код возврата уже проверен отдельным ассертом).

Дизайн — `content/60-implementation/acceptance/2026-08-13-link-form-contract-resolver-at-design.md`.

## Почему shell-suite, а не только pytest

`content/40-architecture/2026-08-13-link-form-contract-design.md` («Контракт с QA-author» →
«Test-pyramid рекомендация») классифицирует AC-008…012 как **integration**, с явным
обоснованием «уже принятый паттерн репозитория (`tests/gramax/catalog-validator/`, ADR-0012
Решение 5)» — то есть сам design-документ указывает на этот прецедент, не на pytest.
QA-author-бриф допускал оба уровня («реши сам, что дешевле поддерживать») — решение: один
уровень (эта директория), не дублирование в `plugins/gramax/scripts/tests/fixtures/`, чтобы не
поддерживать одну и ту же матрицу дважды. Если в будущем понадобится unit-уровень для
`_resolve_link_target` как отдельной функции (например, после появления самого хелпера) — это
дешёвая добавка поверх уже зелёных тестов, не блокирующая эту задачу.

**Итог:** `run.sh` при первом запуске завершается `exit=1` (2 красных / 6 зелёных) —
эмпирически подтверждено (`bash tests/gramax/link-form-resolver/run.sh`). Это ожидаемое и
корректное состояние TDD-цикла: только AC-008/AC-009 требуют НОВОГО кода (второй шаг
инференса `target + ".md"`); AC-010…012 и их edge-варианты — safeguards NFR-001
(«исключительно ослабляющее изменение»), которые ОБЯЗАНЫ уже выполняться сегодня и обязаны
остаться зелёными после FR-082 — красные они означали бы, что даже без нового кода
резолвер уже нарушает контракт AC-010/011/012, что не так.

**Отклонение от буквального прочтения задачи QA-author** («все тесты для AC-008…012 падают
red на текущем коде») — задокументировано явно, не молчаливо: пункты AC-010, AC-011, AC-012
по своей природе — regression guards (см. таблицу FR/NFR mapping design-документа: «AC-010
закрывается 'ловится существующим check_broken_links «по построению», без нового кода'», а
`NFR-001` явно требует «не добавлять новых error там, где сегодня OK»). Форсировать их в
красное состояние значило бы либо тестировать не то поведение, которое требует AC, либо
временно ломать сегодняшний (корректный) резолв ради ложного ощущения «TDD read» — оба пути
хуже честной документации фактического, эмпирически проверенного состояния. Красными
остаются только AC-008/AC-009 — единственные два пункта, для которых сегодняшний код
действительно не содержит требуемого поведения.

## Находка для Dev/SA: `Path.exists()` не различает файл и директорию (`ac-009b`)

Сегодняшний буквальный резолв `(md.parent / target).resolve()` + `.exists()` уже
«резолвит» голую ссылку на директорию (`[X](section)`) просто потому, что директория физически
существует — НЕ потому, что внутри неё есть `_index.md`. Формулировка FR-082 говорит про «не
находит существующий **файл**» — более строгое прочтение потребовало бы `is_file()` на каждом
шаге, а не `exists()`. С таким прочтением директория без `_index.md` внутри перестала бы
резолвиться на шаге 1 (сегодня резолвится) — это НОВАЯ ошибка там, где сегодня OK, что
формально спорит с NFR-001 («кроме случаев, подтверждённых как генуинно битые» — открытая
трактовка, не decided явно требованием). `ac-009b` сознательно не проверяет эту ветку
(директория есть, `_index.md` внутри нет) — поведение не specified требованием, домысливать
его тестом означало бы навязать Dev трактовку, которую BA не зафиксировал. Кандидат на
уточнение SA/BA, если возникнет в реальном корпусе.


Dev тем же шагом, что закрывает FR-082, по прецеденту `tests/gramax/catalog-validator/`
(DEV-002 там же).
