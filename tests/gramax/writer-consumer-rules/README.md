## Находка: буквальная формула AC-002 из требования — vacuous truth через xargs

Буквальная формула AC-002 из текста требования:

```bash
grep -rlE 'code:' plugins/gramax/skills/writer/ \
  | xargs grep -liE 'cross-каталож' \
  | xargs grep -lE '`[A-Za-z0-9_-]+/[^`]+`' >/dev/null && echo PASS
```

**НЕ используется здесь как есть.** Проверено эмпирически на этом окружении (macOS,
`/usr/bin/xargs`, BSD-семантика: команда НЕ запускается при пустом stdin, `xargs` при этом
завершается кодом 0, не ошибкой): когда любая стадия конвейера получает нулевой ввод — что
верно **прямо сейчас** (0 файлов `skills/writer/` содержат `code:`, DEV-004 не начат) — вся
цепочка молча печатает `PASS`, хотя FR-065 не реализован ни на йоту. `>/dev/null && echo PASS`
проверяет только код возврата ПОСЛЕДНЕЙ стадии конвейера (`xargs`), а не то, дошёл ли реальный
результат grep'а до конца цепочки.

Тот же эффект воспроизведён и на дизъюнктном сценарии, который диспозиция называет «ломает
цепочку» (`code:` в файле A, `cross-каталож` в файле B — разные файлы, edge case диспозиции):
проверено вручную на синтетической фикстуре (два файла), цепочка снова тихо возвращает `PASS`
через `xargs`, не `FAIL`, как можно было бы предположить из формулировки диспозиции. Находка
шире предупреждения диспозиции — не просто «цепочка ломается», а «цепочка молча PASS'ит при
любом разрыве, независимо от причины разрыва».

**Исправление** (`ac-002-cross-catalog-code-workflow-example.sh`): цикл по кандидатам без
`xargs`, с явным позитивным предусловием «кандидатов ≥1» перед проверкой совпадения всех трёх
сигналов (`code:`, `cross-каталож`, паттерн `` `A/b` ``) в ОДНОМ файле — тот же семантический
контракт, что и диспозиция называет edge case'ом, но без уязвимого конвейера. Проверено на 3
синтетических сценариях (не закоммичены, воспроизводимы в этом README):
- 0 кандидатов (сегодняшнее состояние) → FAIL по позитивному предусловию.
- Все три сигнала в одном файле (целевое состояние DEV-004) → PASS.
- Сигналы разнесены по двум файлам (edge case диспозиции) → FAIL, корректно, в отличие от
  буквальной формулы.

**Урок для команды:** записан в `content/lessons-learned.md` — `grep | xargs grep | xargs grep`
с завершающим `>/dev/null && echo PASS` — общий паттерн, уязвимый к vacuous truth на любой
платформе, где `xargs` по умолчанию не запускает команду при пустом stdin (macOS/BSD
подтверждено эмпирически; GNU `xargs` при `POSIXLY_CORRECT` может вести себя иначе — не
проверено, не важно для вывода: сам факт platform-dependent тихого PASS уже делает идиому
непригодной для гейта).

## AC-011 — решение PM: диспозиция принята как разрешающий документ, гейт зелёный

Первая версия этого suite'а (до правки PM) держала AC-011 красным: буквальное требование
называло ADR, диспозиция сама объявляла себя «design-документом, не ADR»
(`2026-08-11-writer-rules-disposition.md:20`), а «свободный следующий номер ADR-0014» из
диспозиции успел занять несвязанное решение (`0014-dual-publication-targets.md`, смержено
раньше в тот же день) — существующий gap между буквой AC и фактическим состоянием репозитория
был зафиксирован как открытый координационный вопрос.

**PM решил вопрос явной правкой требования** (см. `content/30-requirements/
2026-08-11-writer-consumer-rules.md`, AC-011, правка датирована 2026-08-11): FR-076 называет
ADR ожидаемой, но не единственной формой разрешающего документа — фактическим разрешающим
документом принята диспозиция (Accepted), которая сама обосновывает, почему она не ADR
(enforcement и машиночитаемый контракт — параллельный ADR-0012, здесь только триаж). Новый
критерий: разрешающий документ существует, ссылается на требование по имени файла и несёт
триаж всех шести тем A–F; каталог размещения (`content/00-project/adr/` либо
`content/40-architecture/`) больше не проверяется.

`ac-011-permitting-adr-references-requirement.sh` переписан под новый критерий — **строже**
прежнего буквального грепа, не слабее: раньше было достаточно, чтобы КАКОЙ-ТО файл в `adr/`
упоминал имя требования; теперь тест явным циклом по кандидатам в ОБОИХ каталогах проверяет,
что тот же файл, который ссылается на требование, несёт заголовки всех шести тем
(`^## A.` … `^## F.`) — отсутствие любой одной темы красит тест, попадание ссылки и триажа в
разные файлы тоже красит тест. Проверено на синтетических фикстурах (полный триаж → PASS;
удалённая тема F → FAIL) — не заведено отдельной постоянной фикстурой, воспроизводимо
вручную по коду теста.

Тест зелёный сегодня — регрессионный барьер, третий после AC-001 и AC-012: если диспозицию
позже отредактируют так, что пропадёт ссылка на требование или одна из шести секций триажа
(A–F), гейт покраснеет. DEV-004 не обязан ничего делать для AC-011 — но и не должен трогать
диспозицию (она вне периметра `plugins/gramax/skills/writer/**`, а сам файл требования и
диспозиция — за пределами задач DEV-004 по «Брифу для Dev»).

## Запуск

```bash
bash tests/gramax/writer-consumer-rules/run.sh; echo "exit=$?"
```

Автономен из любого рабочего каталога (использует `git rev-parse --show-toplevel` и
`$(dirname "${BASH_SOURCE[0]}")` — не полагается на текущий `cwd` вызывающего). Подключён к
`scripts/check.sh --full` (DEV-004); `--fast` не запускает `tests/gramax/**`-suite'ы вообще
(см. форму соседних AC-суитов) и остаётся зелёным независимо от этого suite'а.

Первый прогон: `exit=1`, 9 из 12 скриптов красные, 3 (AC-001, AC-011, AC-012) — зелёные
regression guard'ы — ожидаемое стартовое состояние TDD-цикла, не поломка suite'а.
