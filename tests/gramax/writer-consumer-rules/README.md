## Находка: буквальная формула AC-002 из требования — vacuous truth через xargs

Буквальная формула AC-002 из текста требования:

```bash
grep -rlE 'code:' plugins/gramax/skills/writer/ \
  | xargs grep -liE 'cross-каталож' \
  | xargs grep -lE '`[A-Za-z0-9_-]+/[^`]+`' >/dev/null && echo PASS
```

**НЕ используется здесь как есть.** Проверено эмпирически на этом окружении (macOS,
`/usr/bin/xargs`, BSD-семантика: команда НЕ запускается при пустом stdin, `xargs` при этом
завершается кодом 0, не ошибкой): когда любая стадия конвейера получает нулевой ввод — что
верно **прямо сейчас** (0 файлов `skills/writer/` содержат `code:`, DEV-004 не начат) — вся
цепочка молча печатает `PASS`, хотя FR-065 не реализован ни на йоту. `>/dev/null && echo PASS`
проверяет только код возврата ПОСЛЕДНЕЙ стадии конвейера (`xargs`), а не то, дошёл ли реальный
результат grep'а до конца цепочки.

Тот же эффект воспроизведён и на дизъюнктном сценарии, который диспозиция называет «ломает
цепочку» (`code:` в файле A, `cross-каталож` в файле B — разные файлы, edge case диспозиции):
проверено вручную на синтетической фикстуре (два файла), цепочка снова тихо возвращает `PASS`
через `xargs`, не `FAIL`, как можно было бы предположить из формулировки диспозиции. Находка
шире предупреждения диспозиции — не просто «цепочка ломается», а «цепочка молча PASS'ит при
любом разрыве, независимо от причины разрыва».

**Исправление** (`ac-002-cross-catalog-code-workflow-example.sh`): цикл по кандидатам без
`xargs`, с явным позитивным предусловием «кандидатов ≥1» перед проверкой совпадения всех трёх
сигналов (`code:`, `cross-каталож`, паттерн `` `A/b` ``) в ОДНОМ файле — тот же семантический
контракт, что и диспозиция называет edge case'ом, но без уязвимого конвейера. Проверено на 3
синтетических сценариях (не закоммичены, воспроизводимы в этом README):
- 0 кандидатов (сегодняшнее состояние) → FAIL по позитивному предусловию.
- Все три сигнала в одном файле (целевое состояние DEV-004) → PASS.
- Сигналы разнесены по двум файлам (edge case диспозиции) → FAIL, корректно, в отличие от
  буквальной формулы.

**Урок для команды:** записан в `content/lessons-learned.md` — `grep | xargs grep | xargs grep`
с завершающим `>/dev/null && echo PASS` — общий паттерн, уязвимый к vacuous truth на любой
платформе, где `xargs` по умолчанию не запускает команду при пустом stdin (macOS/BSD
подтверждено эмпирически; GNU `xargs` при `POSIXLY_CORRECT` может вести себя иначе — не
проверено, не важно для вывода: сам факт platform-dependent тихого PASS уже делает идиому
непригодной для гейта).

## Ретировка AC-002 (2026-08-13, ADR-0017) — рабочего рецепта больше нет

**Что проверялось.** `ac-002-cross-catalog-code-workflow-example.sh` (см. предыдущий раздел)
проверял co-occurrence трёх сигналов — `code:`, `cross-каталож`, паттерн inline-code-ссылки
`` `A/b` `` — в одном файле `plugins/gramax/skills/writer/**` как признак того, что FR-065
(«рабочий пример cross-каталожной ссылки через `code`») задокументирован. DEV-004 закрыл этот
AC легитимно: `references/doc-root-schema.md` получил раздел «Cross-каталожные ссылки через
`code`» с реальным `code: GRAMAX-PLUGIN` и рабочей (на тот момент) ссылкой — тест зазеленел по
верной причине, не случайно.

**Почему ретировка, не «AC ещё не реализован».** Отдельная задача (`content/00-project/
adr/0017-cross-catalog-retraction.md`) установила по исполняемому probe RES-006
(`content/10-domain/research/2026-08-13-cross-catalog-links-probe.md`, 10/10 тестов поверх
немодифицированного `linkCreator.getLink()`), что рецепт `code:` **не резолвится ни при каком
внешнем сетапе** — поле `code` резолвером ссылок не читается вообще. FR-065 требовал
задокументировать «рабочий пример»; такого примера никогда не было и быть не могло — посылка,
на которой стоял AC (что описанный `code:`-рецепт вообще является рабочим синтаксисом), стала
известна ложной постфактум. Тот же класс дефекта, что процедура ретировки AC-014
`skills`-поля формализовала в `content/00-project/adr/0011-test-harness-taxonomy.md` Решение 2
(«предмет проверки не существует и не должен существовать ни в одной версии системы») — здесь
предмет проверки существовал (текст был опубликован), но выполнял функцию, которую физически
не может выполнять.

**Обязательное измерение (воспроизводимо).** ADR-0017 Решение 2 предписывает: `doc-root-schema.md`
получает честное объяснение декоративной природы `code`, включающее историческое упоминание
ретированного рецепта («Прежде этот раздел показывал двухшаговый рецепт... построенный на
`code:`... inline code `` `CODE/путь.md` ``»). Проверено эмпирически на репозитории после
правки Dev по ADR-0017:

```
$ grep -rlE 'code:' plugins/gramax/skills/writer
plugins/gramax/skills/writer/references/doc-root-schema.md

$ grep -niE 'cross-каталож' plugins/gramax/skills/writer/references/doc-root-schema.md
70:Прежде этот раздел показывал двухшаговый рецепт cross-каталожной ссылки, построенный на
77:Рабочей замены рецепту здесь не публикуется. Практическая рекомендация для cross-каталожной

$ grep -nE '`[A-Za-z0-9_-]+/[^`]+`' plugins/gramax/skills/writer/references/doc-root-schema.md
72:`` `CODE/путь.md` ``), как перспективный синтаксис. Проверка на реальном резолвере опровергла

$ bash tests/gramax/writer-consumer-rules/ac-002-cross-catalog-code-workflow-example.sh
[PASS] ac-002: рабочий пример cross-каталожной ссылки через поле code найден в одном файле
```

Все три сигнала совпали в одном файле и после ретракции — не потому что рецепт снова стал
рабочим, а потому что честное **историческое объяснение** ретракции неизбежно упоминает те же
три словарных элемента (`code:`, «cross-каталож», пример инлайн-кода в обратных кавычках),
описывая уже отменённое решение. Тест не может отличить «рекомендация» от «пересказ
отменённой рекомендации» по одной co-occurrence — он продолжил бы зеленеть при любой честной
формулировке ретракции. Зелёный тест, охраняющий отменённый контракт, — ложная гарантия;
оставлять как есть было бы противоположностью цели теста (эта находка была явно предсказана
QA-author заранее в `content/60-implementation/acceptance/
2026-08-13-cross-catalog-retraction-at-design.md` → «Находка вне периметра этой задачи»,
до того, как правка была внесена).

**Чем заменено.** Ничем — контракт отменён, не переформулирован. Единственный «рабочий»
пример cross-каталожной ссылки, который FR-065 требовал задокументировать, не существует ни в
какой форме, пригодной для writer-facing документации (ADR-0017 Решение 2 явно отклоняет и
публикацию альтернативного `../../`-рецепта). Замена AC-002 на «проверку отсутствия рабочего
рецепта» дублировала бы `tests/gramax/cross-catalog-retraction/ac-001-doc-root-schema-retracted.sh`
(другой suite, другое требование, уже покрывающее ретракцию по своему контракту) — не
добавляет независимого сигнала, только два теста на один и тот же факт в разных suite'ах.

**Кто санкционировал.** ADR-0017 — архитектурное решение, которое сделало предпосылку AC-002
ложной (не решение об устройстве самого suite'а `writer-consumer-rules`). Ретировка теста в
этом suite — прямое, узкое следствие уже принятого ADR-0017, не отдельное архитектурное
решение об этом suite; выполнено по прямому поручению PM (2026-08-13, задача вне периметра
ADR-0017 «Бриф для Dev»), задокументировано здесь по процедуре ретировки AC
(`content/00-project/adr/0011-test-harness-taxonomy.md` Решение 2) и образцу
`tests/gramax/archive/README.md` → «Ретировка AC о поле `skills`».

**Требование-источник AC-002** (`content/30-requirements/2026-08-11-writer-consumer-rules.md`,
FR-065) **не редактируется** — тот же принцип BR-001/ADR-0017, что Accepted/Done-артефакты не
правятся в теле/статусе задним числом; ретировка исполняемого теста документируется отдельно
(здесь), не стирает след того, что FR-065 когда-то было выполнено легитимно на неполных
данных. Файл `ac-002-cross-catalog-code-workflow-example.sh` удалён из живого suite'а
(`git rm`, история доступна через `git log --follow` по прежнему пути) — не перемещён в
`tests/gramax/archive/`, потому что архив держит целые suite, привязанные к версии релиза
(ADR-0011 Решение 1), а не отдельные ретированные AC внутри всё ещё живого suite.

## AC-011 — решение PM: диспозиция принята как разрешающий документ, гейт зелёный

Первая версия этого suite'а (до правки PM) держала AC-011 красным: буквальное требование
называло ADR, диспозиция сама объявляла себя «design-документом, не ADR»
(`2026-08-11-writer-rules-disposition.md:20`), а «свободный следующий номер ADR-0014» из
диспозиции успел занять несвязанное решение (`0014-dual-publication-targets.md`, смержено
раньше в тот же день) — существующий gap между буквой AC и фактическим состоянием репозитория
был зафиксирован как открытый координационный вопрос.

**PM решил вопрос явной правкой требования** (см. `content/30-requirements/
2026-08-11-writer-consumer-rules.md`, AC-011, правка датирована 2026-08-11): FR-076 называет
ADR ожидаемой, но не единственной формой разрешающего документа — фактическим разрешающим
документом принята диспозиция (Accepted), которая сама обосновывает, почему она не ADR
(enforcement и машиночитаемый контракт — параллельный ADR-0012, здесь только триаж). Новый
критерий: разрешающий документ существует, ссылается на требование по имени файла и несёт
триаж всех шести тем A–F; каталог размещения (`content/00-project/adr/` либо
`content/40-architecture/`) больше не проверяется.

`ac-011-permitting-adr-references-requirement.sh` переписан под новый критерий — **строже**
прежнего буквального грепа, не слабее: раньше было достаточно, чтобы КАКОЙ-ТО файл в `adr/`
упоминал имя требования; теперь тест явным циклом по кандидатам в ОБОИХ каталогах проверяет,
что тот же файл, который ссылается на требование, несёт заголовки всех шести тем
(`^## A.` … `^## F.`) — отсутствие любой одной темы красит тест, попадание ссылки и триажа в
разные файлы тоже красит тест. Проверено на синтетических фикстурах (полный триаж → PASS;
удалённая тема F → FAIL) — не заведено отдельной постоянной фикстурой, воспроизводимо
вручную по коду теста.

Тест зелёный сегодня — регрессионный барьер, третий после AC-001 и AC-012: если диспозицию
позже отредактируют так, что пропадёт ссылка на требование или одна из шести секций триажа
(A–F), гейт покраснеет. DEV-004 не обязан ничего делать для AC-011 — но и не должен трогать
диспозицию (она вне периметра `plugins/gramax/skills/writer/**`, а сам файл требования и
диспозиция — за пределами задач DEV-004 по «Брифу для Dev»).

## Запуск

```bash
bash tests/gramax/writer-consumer-rules/run.sh; echo "exit=$?"
```

Автономен из любого рабочего каталога (использует `git rev-parse --show-toplevel` и
`$(dirname "${BASH_SOURCE[0]}")` — не полагается на текущий `cwd` вызывающего). Подключён к
`scripts/check.sh --full` (DEV-004); `--fast` не запускает `tests/gramax/**`-suite'ы вообще
(см. форму соседних AC-суитов) и остаётся зелёным независимо от этого suite'а.

Первый прогон: `exit=1`, 9 из 12 скриптов красные, 3 (AC-001, AC-011, AC-012) — зелёные
regression guard'ы — ожидаемое стартовое состояние TDD-цикла, не поломка suite'а.
