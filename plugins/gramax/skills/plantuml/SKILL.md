# PlantUML и BPMN для Gramax

Skill пишет PlantUML-исходник (включая Salt-макеты интерфейсов) или BPMN-процесс (Camunda XML) в файл рядом со статьёй и вставляет тег-ссылку в md-документ. Работает без MCP, без скриптов, без preview, без внешних инструментов: только Write/Edit/Read. Создаёт два артефакта — исходник (`.puml` или `.bpmn`) и тег-ссылку в md. Рендер — исключительная работа движка Gramax (см. «Стоп-правило»).

## When to use

- Пользователь просит PlantUML-диаграмму: «нарисуй plantuml / plant-uml / puml», «UML-диаграмма» — компоненты, развертывание, активности, таймлайны, sequence и другие типы PlantUML.
- Пользователь просит макет интерфейса: «Salt», «макет интерфейса», «макет экрана/формы/диалога».
- Пользователь просит BPMN-процесс: «bpmn», «BPMN-процесс», «Camunda» — процесс, который должен остаться редактируемым в BPMN-инструментах.

**Не для:** mermaid-диаграмм → `gramax:mermaid`; drawio / `.drawio` / SVG-схем через drawio → `gramax:drawio`; preview и локального рендера диаграмм (см. «Стоп-правило»). Неявный запрос («нарисуй диаграмму» без указания движка) навык не перехватывает — владелец уточняющего вопроса `gramax:mermaid`; его fallback-диалог содержит plantuml и bpmn как отдельные опции.

## Workflow

1. Прочитай запрос; определи формат: PlantUML (вкл. Salt) или BPMN (Camunda XML).
2. Определи `target_page` (md-файл статьи). Если не указан — спроси пользователя.
3. Предложи имя файла по naming convention (см. раздел «Naming convention»): `<page-slug>-<diagram-slug>.puml` или `<page-slug>-<diagram-slug>.bpmn`. Запроси подтверждение.
4. **Коллизия:** если файл с таким именем уже существует — прочитай его первые 5 строк, покажи содержимое пользователю и предложи три опции: перезаписать / выбрать другое имя / отменить. Без явного «перезаписать» — не трогай файл.
5. Сгенерируй исходник по правилам раздела «PlantUML» или «BPMN (Camunda XML)» ниже; при затруднениях — справочник из «References».
6. Создай файл через **Write tool** в той же директории, что и `target_page` (не в assets-папке). Файл содержит только чистый исходник, без Gramax-разметки и обёрток.
7. Вставь тег-ссылку в md через **Edit tool** (см. «Теги вставки»): самозакрывающийся тег, с пустой строкой до и после.
8. Сообщи пользователю, какие файлы созданы/изменены, и оговорку окружения рендера (см. «Окружение рендера»).

## PlantUML

`.puml`-файл содержит чистый PlantUML: каркас `@startuml`/`@enduml`, без Gramax-разметки и без обёрток (внутри файла нет `<plant-uml`, нет ` ```plant-uml ` — только DSL).

```
@startuml
package "auth" {
  [Session]
  [TokenStore]
}
[Session] --> [TokenStore] : validate
@enduml
```

Поддерживаются типы PlantUML: component, deployment, activity, timing, sequence, use case, state и другие — полный синтаксис PlantUML; типовые ошибки и каркасы — [`references/plantuml-syntax.md`](references/plantuml-syntax.md).

### Salt (макеты интерфейсов)

Salt — часть PlantUML-авторства, отдельного механизма нет: макет интерфейса (окно, форма, диалог) пишется Salt-нотацией `@startsalt`/`@endsalt` в тот же `.puml`-файл и вставляется штатным тегом `<plant-uml path="…"/>`.

```
@startsalt
{ Логин | "Логин" | "Пароль" | [Войти] }
@endsalt
```

## BPMN (Camunda XML)

BPMN-процесс — файл `.bpmn` с Camunda XML. Документированная форма — только файловая; inline-вариант для bpmn в документации движка не существует и не выдумывается.

Каркас: первая строка `<?xml version="1.0" encoding="UTF-8"?>`, корневой элемент `bpmn:definitions` (или `definitions` в BPMN-namespace); минимальный пример и типовые ошибки — [`references/plantuml-syntax.md`](references/plantuml-syntax.md).

**Verify-оговорка:** авторство ведётся по документированной форме (`<bpmn path="…"/>`), но рендер тега `<bpmn>` на проверенном окне движка не подтверждён — проверь в своём окружении (verify-before-include; релизный runtime-probe — чек-лист PM). Рендер — ответственность движка; локальная конвертация не строится ни в каком исходе (см. «Стоп-правило»).

## Теги вставки

**PlantUML (вкл. Salt):**

```markdown
<plant-uml path="./overview-component-diagram.puml"/>
```

**BPMN:**

```markdown
<bpmn path="./process-order-flow.bpmn"/>
```

- Оба тега самозакрывающиеся (`/>`), вставляются с пустой строкой до и после.
- `path` — относительная ссылка на файл рядом со статьёй (`./<имя>.puml`, `./<имя>.bpmn`).
- Атрибуты `<plant-uml>` сверх `path` — `title`, `width`, `height`, `float`, `scale` (схема движка) — только по явному запросу пользователя. Дефолтные размеры не изобретаются: пустое поле лучше правдоподобного — размеры не подставляются, пока пользователь не попросил. Значения `width`/`height` — со спецификатором (например, `800px`).
- У `<bpmn>` документирован только `path`; остальные атрибуты не домысливаются.

## Naming convention

Правило: `<page-slug>-<diagram-slug>.puml` / `<page-slug>-<diagram-slug>.bpmn` — конвенция единая с mermaid, меняется только расширение; второй параллельной конвенции нет.

### Формирование `<page-slug>`

- Берётся имя md-файла (`target_page`) без расширения.
- **Специальный кейс:** если файл называется `_index.md` — берётся имя родительской директории.
- Примеры: `docs/auth/overview.md` → `overview`; `docs/auth/_index.md` → `auth`.

### Формирование `<diagram-slug>`

- Тематическое имя из запроса: ключевые существительные процесса/системы.
- Kebab-case, только ASCII, не более 30 символов; длиннее — обрезать до 30, сохраняя целые слова.
- Тема не названа явно — fallback `diagram`.
- Кириллица — предложить два варианта на выбор: семантический перевод на английский и ввод slug вручную пользователем (механическое преобразование названия не выполняется — прецедент mermaid).
- Символы `:`, `*`, `?`, `"`, `<`, `>`, `|`, `\`, пробелы → заменять на `-`.

### Примеры

| md-файл | Тема запроса | Предложенное имя |
|---------|--------------|-----------------|
| `docs/auth/overview.md` | «диаграмма компонентов» | `overview-component-diagram.puml` |
| `docs/process/_index.md` | «процесс заказа» | `process-order-flow.bpmn` |
| `docs/api/overview.md` | (не указана) | `overview-diagram.puml` |

## Backward compatibility (inline-форма)

Канон плагина — file-based (файл + тег-ссылка), единый с mermaid. При чтении `target_page` проверяй наличие inline-блока устаревшей формы ` ```plant-uml ` (в т.ч. с опциями `{title, scale, float}`).

**Обнаружен inline-блок ` ```plant-uml `:**

```
Обнаружен inline-блок plant-uml в статье — канон плагина: файл + тег-ссылка.
Предлагаю точечную миграцию: извлечь исходник в файл <page-slug>-existing.puml
и заменить блок на тег <plant-uml path="./<имя>.puml"/>.
Опции блока переносятся в атрибуты тега 1:1: title → title, scale → scale, float → float.
Выполнить миграцию? (да / нет)
```

**Без явного подтверждения пользователя — файл не трогать.** Навык не выполняет миграцию молча. Пакетная миграция inline-блоков по каталогу — вне scope навыка.

## Окружение рендера

Рендер PlantUML/Salt требует настроенного рендера диаграмм движка (`DIAGRAM_RENDERER_SERVICE_URL` — облако/GES; рендер серверный). В окружении без рендер-сервиса диаграмма не отобразится (ошибка движка `no-diagram-renderer`) — это свойство окружения, не дефект авторства. Навык авторит исходники в любом окружении. Поддержка Salt конкретной конфигурацией рендер-сервиса проверяется релизным probe (тот же verify-контур, что у `<bpmn>`).

## Стоп-правило

Навык никогда не конвертирует `.puml`/`.bpmn` в SVG/PNG и не вызывает локальных рендеров (PlantUML/Java, npm, draw.io desktop). Единственные артефакты навыка — исходник и тег-ссылка в статье; производные файлы (SVG/PNG) не создаются, рендер — исключительная работа движка. Если формату понадобился локальный рендер/конвертация для отображения — это стоп: эскалация пользователю к SA/PM, не строительство pipeline (анти-ADR-0008).
