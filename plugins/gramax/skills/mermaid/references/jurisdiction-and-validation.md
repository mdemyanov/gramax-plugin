# Граница юрисдикции file-based mermaid и валидация вынесенного файла

Развёрнутый справочник к короткой формулировке в `SKILL.md` § «Gramax-интеграция». Загружай
по требованию — при работе с потребительским `content/`-валидатором, при аудите каталога на
устаревший формат, при вопросе «распространяется ли file-based mermaid на этот файл».

ADR: `content/00-project/adr/0013-mermaid-adoption-and-migration.md` (Решения 1, 2, 5).
Дополняет `content/00-project/adr/0010-mermaid-file-based-workflow.md` (ground-truth формата).

## Граница юрисдикции (Решение 1)

Контракт file-based mermaid (`<mermaid path="…" width="…" height="…"/>`, ADR-0010) действует
**внутри поддерева, чей ближайший предок несёт `.doc-root.yaml`** — то есть внутри
Gramax-рендерящегося каталога. За пределами этой границы — инженерные документы репозитория
(`docs/`, планы исполнения, README, `CLAUDE.md` и аналоги) — инлайн-mermaid **не является
нарушением** контракта плагина.

**Примеры:**

| Файл | `.doc-root.yaml`-предок? | Юрисдикция |
|---|---|---|
| `content/40-architecture/foo.md` (рядом `content/.doc-root.yaml`) | да | в юрисдикции — инлайн должен мигрировать на тег |
| `docs/onboarding.md` (инженерный документ, `.doc-root.yaml` нигде выше нет) | нет | вне юрисдикции — инлайн не нарушение |
| `content/legacy/nested/page.md` при вложенном `content/legacy/.doc-root.yaml` | да (ближайший, не корневой) | в юрисдикции — вложенные `.doc-root.yaml` не требуют спецкейса, каждый узел ищет своего ближайшего предка |

Если у репозитория несколько `.doc-root.yaml`-каталогов (в том числе вложенных) — правило не
меняется: для каждого файла берётся его собственный ближайший предок, независимо от других
каталогов рядом.

## Предикат «валидный `.mermaid`-файл» (Решение 2, вариант b)

Способ для потребителя убедиться в содержимом вынесенного файла, не отключая file-based
workflow целиком и не давая ему слепого доверия. Файл соответствует формату, если верно всё:

- расширение `.mermaid`;
- лежит рядом со страницей-источником (та же директория, не подпапка `assets/`);
- имя следует `<page-slug>-<diagram-slug>.mermaid` (ADR-0010 Решение 2);
- первая непустая строка — один из 8 поддерживаемых Gramax-типов: `flowchart`,
  `sequenceDiagram`, `gantt`, `classDiagram`, `stateDiagram-v2`, `erDiagram`, `pie`, `mindmap`;
- содержимое не несёт Gramax-разметки — ни `<mermaid>`, ни fenced ` ```mermaid ` — только
  чистый DSL.

Предикат язык-независим — потребитель реализует проверку на своём стеке (Python, TypeScript,
что угодно); плагин не поставляет исполняемый чекер для чужого репозитория (см. «Периметр»
ниже).

## Класс конфликта: валидатор потребителя не видит файлы вне `*.md`

Часть репозиториев-потребителей поддерживает собственный `content/`-валидатор, который по
конструкции обходит только файлы `*.md` (allowlist суффиксов ограничен `.md`). Под таким
allowlist'ом `.mermaid`-файл, который создаёт file-based mermaid (ADR-0010), для валидатора
невидим — с точки зрения гейта такого файла как будто не существует, его содержимое вообще не
проверяется.

Это факт о том, как **устроен** такой валидатор, а не утверждение о том, что рендерит Gramax.
Фактический контракт рендера Gramax задокументирован как ground-truth в
`plugins/gramax/skills/writer/references/blocks.md`: самозакрывающийся тег
`<mermaid path="…" width="…" height="…"/>` ссылается на внешний `.mermaid`-файл, и Gramax
рендерит его. Слепота allowlist-валидатора на суффиксы вне `.md` — причина невидимости файла;
поведение рендера Gramax тут ни при чём.

### Пример расширения allowlist (иллюстрация, не готовый патч чужого репозитория)

```python
# ПРИМЕР для иллюстрации предиката выше — НЕ артефакт, который этот плагин ставит в ваш
# репозиторий. Адаптируйте под свой валидатор самостоятельно (FR-063: правки только внутри
# gramax-marketplace).
ALLOWED_SUFFIXES = {".md", ".mermaid"}
```

**Одного расширения allowlist недостаточно.** Само по себе добавление `.mermaid` в allowlist
разрешает файлу существовать для гейта, но не проверяет его содержимое — это и есть слепое
доверие невидимому файлу, которое исходное намерение валидатора (детекция посторонних/битых
файлов в `content/`) как раз должно исключать. Дополните расширение allowlist фактической
проверкой по предикату выше — либо собственной реализацией, либо вызовом
`plugins/gramax/scripts/migrate_mermaid.py` этого плагина (офлайн-скан, без мутаций в режиме
по умолчанию) как одного из источников сигнала. Так исходное намерение гейта не ослабляется.

## Локальный оверрайд легитимен (Решение 5)

Потребитель вправе в границах своего собственного репозитория (свой `CLAUDE.md`, свой
валидатор) закрепить обратное правило — инлайн вместо file-based. Плагин не считает такое
расхождение дефектом, который нужно устранять, и не принуждает к консистентности за пределами
своей юрисдикции (BR-004). Этот документ не называет и не оценивает решение конкретного
внешнего репозитория — только сам класс конфликта и факт контракта рендера, названные выше.

## Периметр (FR-063)

Ни этот справочник, ни `migrate_mermaid.py` не вносят правок ни в один репозиторий вне
`gramax-marketplace`. Всё, что описано выше, — возможность плагина, которую потребитель
применяет к себе сам.
